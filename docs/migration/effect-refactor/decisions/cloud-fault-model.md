# Candidate cloud fault expectations

This packet defines independent synthetic outcomes before a different author implements cloud adapters. It is planning evidence, with no executed service, crypto, database, provider or real-data proof. The machine-readable [cases](cloud-fault-cases.json) are the literal oracle; their format version is local to this task, not a public protocol. Alpha and beta, record/day labels, roles and key versions are symbolic. No capacity, timing, retention, billing, provider or region value is selected.

The accepted BASE-CLOUD inventory pins a legacy whole-envelope HMDC1/AES-GCM source, exact originals, day-level projection heads, separate writer/owner/agent credentials and durable lost-response reconciliation. Its test names and fixture bytes supply provenance, not execution evidence. Its restore fixture proves an isolated synthetic snapshot scenario in source; it does not specify restoring an old backup after later accepted deletion or revocation. This packet adds that independent expectation explicitly. Pilot whole-object authentication, unbound listing cursors, account/day heads and numerical constants do not become successor contracts.

Reserve, receive, verify and seal keep staging invisible. Every contributing authentication unit must finish authentication before any plaintext from that unit is released. A whole-object legacy unit requires whole-object verification even for a narrow plaintext range; a future framed design must bind its complete units and ordered manifest independently. Hash checks, provider success responses and a valid ciphertext prefix are insufficient. Canceling a stalled or partial unit cannot expose its prefix.

Objects and SQL commit separately. The SQL boundary commits the original ledger identity, once-only accounting and projection outbox together. A lost response is resolved by exact durable postconditions; unreadable verification remains pending. It never authorizes deletion of an object that may belong to a committed winner or release of an unknown reservation. Abort claims race with commit/renewal durably, and acknowledge cleanup only after verified absence. A committed winner needs a separately authorized erasure operation. Stored receipts describe original commitment; ready receipts describe a particular projection version, frontier and coverage.

Original bytes remain exact. Broad and narrow exports retain independent immutable original identities. A newer narrow generation changes only its selected source/installation/fields; omitted broad fields retain their older provenance and freshness. Stable source record identity can deduplicate overlapping ranges within a reviewed lineage. Matching timestamps or values across devices, sources, schemas or reducers cannot establish equivalence. Arrival time does not replace producer generation authority. Legacy absent installation, selection, profile or session identity stays absent. Reindexing is a labeled derivative, with pinned codecs/reducers and current suppression.

Every query page and raw materialization rechecks current tenant, account, source, purpose, recipient, range, detail and existing/future-upload authority. A pinned query frontier never freezes away revocation. Wrong-tenant/query/source/version cursors fail closed. Writer, reader, owner and status credentials have independent authority; sign-in, purchase, native permission or recovery does not create a new source or agent grant. Forbidden or unsupported purpose/recipient paths stay unavailable. OAuth, recovery and numerical revocation policies remain candidate contracts requiring separate review.

Later accepted deletes and revokes persist in an independent authoritative suppression journal before durable acceptance acknowledgment. Restore starts in quarantine. It must obtain an authenticated complete journal matching the restored tenant/service lineage and a latest independently trusted frontier outside the old backup lineage, including later accepted events. Authentic but stale, incomplete, unavailable or wrong-lineage journals block serving, refresh, projection and promotion. Old backups, reader rollbacks, old key versions and replayed outbox entries cannot resurrect access or data. A journal's assertion that it is current cannot establish its own freshness.

Erasure scopes include containing immutable artifacts, object versions, manifests, projections, indexes, keys, caches, replicas, temporary copies and backups. Selective deletion may require removing the whole containing original, with collateral unavailability disclosed, or a separately reviewed new-artifact transaction. Neither immediate crypto-erasure nor provider-copy expiry is promised. Server revocation cannot recall plaintext already held by an independent recipient; controlled onward copies need their own purge evidence.

Q-CLOUD-REGION, Q-CLOUD-TOPOLOGY, Q-CLOUD-IDENTITY, Q-CLOUD-RETENTION, Q-CLOUD-COMMERCE and Q-CLOUD-GRANTS remain open at the assigned source. Concrete owners and resolution criteria are copied into the case file. H02/H03/H04/H05/H07 and the cloud decomposition tasks consume these expectations after independent review. Executable tests, source-purpose admission, each exact client, actual provider fault/restore/erasure measurements and production rollout remain separately scoped. Local account-free use and current native/Rust/pilot historical authority remain intact.
