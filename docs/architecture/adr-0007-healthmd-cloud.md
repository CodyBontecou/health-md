# ADR-0007: Isolated, opt-in Health.md Cloud export receiver (draft)

## Status

**General-purpose production cloud remains unapproved.** The original synthetic preview rejects all export uploads and token creation. The owner authorized an explicitly disposable, unbacked single-user VM pilot, with its original writer tailnet-only, a dedicated public write-only `api.healthmd.app` ingress to the same encrypted store, and a separately authenticated public read-only MCP endpoint at `mcp.healthmd.app` now deployed with a separately issued aggregate-only Muse token (its actual client connection is unverified). Existing credentials cannot access the new opt-in `full_export` scope; a separately consented full-export Muse token was subsequently issued, with actual client capture still unverified. The owner accepts permanent data-loss risk and does **not** require backup/restore or independent external security-review sign-off for this pilot. This does not make the pilot durable, certified, regulated, or a general public signup service; public privacy statements must accurately describe any actual processing. Proposed ADR-0008 defines a separate future multi-user production boundary and does not supersede or authorize changes to this pilot unless it is explicitly accepted.

## Neutral outcome and mobile compatibility

A user can explicitly send selected daily exports to a private, account-bound HTTPS destination, see delivery and current-day inventory, and download original envelopes. Both iOS and Android already support a user-entered compatibility **API Endpoint** URL and Bearer token; no mobile setting, public daily schema, direct protocol, fixture, or exporter is changed. Apple sends `healthmd.api_export` v1/v2 around Apple `healthmd.health_data` v8; Android compatibility mode sends v1 around frozen Android v4. The receiver branches on envelope version and daily version, stores the original bytes without transforming OS-specific data, and reports unsupported versions as errors. Android **Raw API Snapshot** is a different contract and is not accepted here. No fabricated shared metric semantics or provider values.

Affected producers/consumers: Apple API Endpoint client, Android compatibility API Endpoint client, a new cloud receiver/dashboard, website privacy/docs and external integrations *at launch*. CLI, shared core, Obsidian plugin, mobile producers and direct protocol are unchanged by the separate, deployed VM read-only MCP API; no producer bytes or daily export schema change. The proposed common v9 profile is not silently accepted. User-facing staging is dashboard documentation only; there is no new iOS/Android cloud affordance yet.

## Boundary

`apps/cloud` is an independent Node/Cloudflare Worker component with its own lockfile, D1 database, private R2 bucket, email delivery secret, authentication secrets, deployment identity, CI, and migrations. A separate **VM-native adapter in the unbacked owner-operated pilot, not approved for general production**, maps the D1/R2 interfaces to owner-only SQLite and a private application-encrypted ciphertext directory on the EXE.dev VM. The original writer remains on loopback behind a dedicated Tailscale Serve HTTPS port; an independent write-only public listener, proxy and Cloudflare Tunnel now accept authenticated compatibility exports without exposing the account or read routes. The pilot uses a single offline-provisioned username/password account instead of email delivery. Its secrets, backup, and deployment identity must be distinct from the Wrangler synthetic preview. It does not reuse or communicate with Practice (synthetic-only clinical boundary), website, wake, pricing analytics, or OAuth broker storage. The website must not serve the authenticated dashboard or proxy exports. API Endpoint sends iPhone → cloud endpoint directly; no hidden collection occurs. The app remains fully useful without a cloud account. Third-party model access is possible only via a separately issued reader token: the owner authorized an aggregate-only Muse token under Muse default Meta handling, with client-side capture not yet verified. No public anonymous access or write-token read access exists.

## Prototype controls

- The Worker profile uses invitation-only email-link accounts (public signup explicitly refused); generic sign-in response, IP/email HMAC rate limits, 15-minute single-use link, hashed session IDs, HttpOnly SameSite=Strict Secure production cookies, Origin check for browser mutations. The optional VM password profile has no HTTP signup or password reset; it uses an offline single-user bootstrap, keyed username lookup, versioned salted PBKDF2-SHA256 (600,000 rounds) with a separate 32-byte HMAC pepper, generic authentication failures, per-IP/username rate buckets, and reauthentication for an account-deletion request. Its loopback proxy and password design require controlled auth, origin and abuse tests; the owner did not require independent external-review sign-off for the disposable pilot. Delivery via a transactional email provider requires its own privacy, data-processing, and regional review. No email address or raw IP is kept in D1: email ciphertext + keyed lookup, HMAC rate bucket. The sender still necessarily receives the destination email.
- Dashboard issues randomly generated **write-only** per-device ingest tokens, stores only hashes and last four characters, and supports explicit revocation. Tokens cannot read account, download, or invoke MCP APIs. Signed-in browser sessions cannot ingest without an independent ingest token. Cross-origin browser reads are not supported.
- POST `/api/v1/exports` requires HTTPS in production, `Authorization: Bearer hmd_ing_…`, JSON, a bounded body (default 25 MiB), structural checks of API v1/v2 and supported daily versions, and account/rate quotas. The checks are **not a full validation of every nested health field or provider record**. It returns 2xx only after an encrypted R2 object and transactional D1 metadata/daily-pointer commit. Failure-only envelopes remain valid and do not create fictitious daily records.
- One envelope is retained as exact UTF-8 plaintext *inside application-encrypted R2 ciphertext* (or private VM filesystem ciphertext in the unapproved VM profile). AES-256-GCM with random per-object HKDF salt and nonce binds account/export identity as authenticated data. Object key is random; key ID and metadata remain in D1. Source migrations `0011_account_export_keys.sql` and `0013_account_key_rewrap.sql` add random per-account data-encryption keys wrapped under versioned AES-256-GCM production KEKs with account/key/version AAD and bounded idempotent KEK rewrapping; split production profiles require this mode, preserve legacy reads, and fail closed on missing historical KEKs or tampering. It is source-only and not applied to the legacy-key VM pilot. Email has separate AES-GCM encryption with a distinct identity secret. Worker key material stays in Wrangler secrets; VM key custody has not been approved. Ciphertext remains readable only with the correct historical key ID, account ID, and export ID. No public bucket URLs or health payloads in D1 or logs. Cloudflare infrastructure still handles transport before encryption and retains the service keys; this is **not end-to-end or zero-knowledge encryption**.
- D1 retains account/authorization state, health *owner dates*, envelope versions/source, byte counts, statuses, receipt times, and hashes. Dates and status are sensitive metadata; the dashboard and D1 are part of the health-data boundary. D1 points to the newest accepted snapshot per account and owner day using normalized `exported_at`. A retry with identical bytes returns the original receipt; an older but different export remains archived without replacing a newer current-day pointer. Full envelopes remain downloadable by their owner only, individually or in bounded five-envelope TAR portability pages that verify stored hashes and do not stage plaintext archives. No semantic-query database exists.
- The Worker emits no application logs containing user data, uses no-store responses and static strict CSP, and has no third-party scripts or wildcard CORS. Host binding to one origin, no query parameters, and no reflected payload in errors are enforced. Server-side monitoring still requires a privacy-specific provider audit before launch.

## Invariants and residual hazards

The backend uses ordinary Worker Web Crypto and whole-envelope JSON parsing/encryption, not a streaming large-artifact path. The 25 MiB limit can still stress Worker memory; a single lossless day can exceed it. The live pilot's account quota remains a best-effort check until its next controlled migration. Source migration `0010_multi_user_ingest.sql` adds a durable per-account committed/reserved-byte ledger, two active upload intents per account, pre-object quota reservation, exact-retry identity, and expired-intent reconciliation; it is verified in synthetic VM and local-D1 migration tests but is not yet live. The original VM writer is `flock`-protected and serializes uploads within that process. Public ingest has its own bounded per-process queue, so the two listeners can upload concurrently; after migration `0010`, correctness relies on the shared durable account ledger rather than either process-local queue. Rate limits are D1 transaction-window counters, not a substitute for edge WAF/bot defenses. D1 and R2 do not share a transaction: a failed D1 commit triggers R2 deletion, but an R2 deletion failure can leave encrypted orphan ciphertext. Source migration `0014_maintenance_cursors.sql` and the split maintenance profile now add a bounded, cursor-persisted R2 orphan scavenger that preserves export/upload-intent references and fails closed on provider or unexpected-key errors; it is tested synthetically but not deployed or exercised against a production bucket. The VM personal-MVP profile checks missing ciphertext and removes unreferenced encrypted files at startup and during serialized maintenance; this is not a substitute for backups. Earlier envelopes are retained for revision history. The owner's personal-MVP choice is **unlimited revision retention** (`REVISION_RETENTION_DAYS=unlimited`), so scheduled age-based expiry is disabled; a finite policy remains supported only when explicitly configured. This does not lift the account's storage quota or provide durability. A deletion request disables the account and queues idempotent envelope removal; source migration `0012_deletion_status_receipts.sql` adds a hashed, expiring bearer receipt that reports only pending/completed after sessions are revoked, while an expired receipt never removes an unfinished job. A scheduled worker can expire superseded envelopes only under an explicit finite policy. Backup expiry and restore are not provided in this disposable pilot: loss of this VM or key material can permanently erase all retained exports. The writer uses explicit risk acknowledgement, HTTPS on a separate tailnet port, private storage, real password login, serialized ingest/quota, startup/periodic orphan reconciliation and deletion checks. The separately deployed public MCP reader must never gain writer credentials or filesystem write access; re-test those boundaries on every reader change. No external-audit or recoverability claim is made.

## Disposable single-user public MCP pilot conditions

1. Keep the writer's private tailnet ingress, preview, website and other port-443 service unchanged. Route only `mcp.healthmd.app/mcp` over HTTPS to a loopback-bound, independently authenticated reader process.
2. A read token must never authorize writes or browser/dashboard access. Demonstrate a distinct reader Unix identity, group-read-only encrypted objects/SQLite, a read-only service mount, token revocation, bounds and negative cross-account tests before enabling ingress. Disable caching and health-data/credential logging at the proxy.
3. The owner accepts permanent data loss with no off-host backup, password reset or historical key recovery. Do not claim durability or independent security certification. Keep deletion/erasure behavior and truthful retention/privacy disclosures visible.
4. Before issuing a credential to any hosted agent, identify its actual product, connection/auth support and retention terms, and obtain the owner's consent for its exact read scope. Muse default use of the aggregate and later full-export scopes was separately authorized; Grokbot has not been qualified or authorized. Never put credentials into a URL or reuse the ingest token.
5. The checked-in Worker still has placeholder bindings and is not this VM pilot. A general-purpose multi-user Cloudflare production release would need a separate plan and owner approval, not an implied rollout from the pilot.

## Remote retained-export MCP decision (live disposable pilot)

The VM has a separately installed read-only MCP process with its own expiring/revocable per-user `hmd_read_` bearer credentials and offline operator administration. Existing/default `aggregates` tokens read only selected Apple-v8 daily metric projections. Newly and explicitly issued `full_export` tokens can navigate and reconstruct **any original retained, account-owned API-export JSON envelope** in bounded child/byte pages, including historical revisions, archived source data and provider sidecars; they cannot mutate data or read arbitrary VM paths. It does not add a route or read credential to the Worker, VM writer/dashboard, Apple/Android exporters, CLI or direct protocol. `apps/cloud/docs/remote-read-only-mcp.md` specifies the reader's caps, exact source/metric constraints, private process boundary, synthetic tests and deployed dedicated HTTPS ingress. A write-only export token and browser session are **not** MCP credentials.

The owner selected `mcp.healthmd.app`; a dedicated loopback MCP reader, isolated local proxy and Cloudflare Tunnel are deployed on that hostname. Public HTTPS requests without a read token fail with 401; the temporary deployment smoke token was revoked. Subsequently, a dedicated aggregate-only Muse token was issued after consent to Muse default data handling, though Muse's actual connector has not been confirmed. The owner explicitly waived backup/restore and independent external-review sign-off for this disposable one-user pilot; both remain **absent**, not silently satisfied. The live reader runs under a distinct UID with group-read-only encrypted files/SQLite, a read-only systemd mount and no access to writer secrets. Synthetic and controlled live tests checked owner-scoped read calls, ingest-token rejection, revocation, limited response shape and denied writes; client-specific interoperability remains unqualified. A hosted client that safely stores per-host bearer headers may use a distinct revocable read token after owner consent; a client requiring OAuth discovery needs a separate OAuth/PKCE design rather than a token in its URL. Aggregate-only tokens cover eleven curated Apple-v8 metrics in bounded time windows, not per-metric grants. The owner later explicitly consented to an expanded Muse default-experience read scope for **all currently retained** data points, including sensitive archives, locations, mental/clinical details, provider sidecars and exact binary-bearing JSON bytes. No pre-existing token may silently inherit that scope: a new full-export token was issued and must be captured in Muse's private vault, with the original revoked after verified client rotation. No Grokbot token or product qualification exists. The full tools are documented in `apps/cloud/docs/mcp-full-export-tools.md`; all results remain bounded and audited without health-bearing logs.
