## Vocabulary and trust partitions

- **Account identity**: existing server-owned account key in one issuer/environment, established by that authority's browser login. Not an email string, provider ID, purchase receipt or CLI peer.
- **Installation session**: independently revocable native session family linked to an account, public client registration and random installation ID. The ID is not a credential, hardware attestation or cryptographic sender constraint. Tokens remain bearer secrets; copying one is a residual risk.
- **Configuration principal**: result of authenticating a native access token for one configuration audience. Only account/installation/session IDs and approved scopes; no browser cookie/password/email/health fields.
- **Portable content**: the allowlisted profile settings and inert intents in E08; never an opaque native settings snapshot.
- **Local mapping**: `(issuer, environment, account_id, cloud_profile_id) -> native_profile_id`, base revision/hash, sync selection and local apply status. Mapping is installation-local; native IDs never become cloud profile IDs.
- **Execution authority**: local destination/grants/credentials, entitlements, health permissions, engine pins and user confirmation. No synced content or configuration credential supplies it.

Trust partitions stay distinct: account configuration, browser retained-health reads, write-only receiver, request transport, MCP reader, native OS health store, direct CLI/MCP pairing, and provider OAuth. The isolated account authority lives within the Cloud sensitive-data domain; no website, Practice, wake, analytics or provider OAuth broker code/bindings/secrets may become its login proxy (E02–E07).

## Native authorization adjunct (AS02 interface)

Exact source route names and query/body rules are in [the contract](../../packages/contracts/account-auth/v1/contract.md). Only `GET /account/authorize` may receive the narrowly allowlisted non-secret authorization query. Existing account/auth/profile/read/ingest routes retain query rejection. On invalid client/redirect/audience, render a fixed local error: never redirect to an unverified callback. Neither tokens nor health selectors appear in the browser URL.

1. Native app creates a per-attempt random state and PKCE verifier in private temporary state, binds the selected issuer/environment/client/callback/installation and account-generation fence, then opens the **system browser**, not an embedded credential form. Apple targets use the native authentication-session interface; Android Play and F-Droid use a system browser/Custom Tabs interface without Google identity dependencies. Native app receives no password, email link or copied cookie.
2. Browser uses its existing authenticated identity, or signs in through its existing password/email-link route. It returns to a validated same-origin pending authorization transaction. Explicit consent names the native client, account, environment and requested configuration scopes. A browser account change invalidates the pending decision and requires a new review. No login method grants scopes by itself.
3. Same-origin, CSRF-bound `POST /api/account-auth/v1/decision` commits the exact account/client/callback/challenge/scope tuple and a single-use code. Callback carries only `code`, `state`, `iss` (or fixed `error`, `state`, `iss`), never access/refresh tokens, user/account IDs or health scope. No redirect on failed registration validation.
4. Native raw callback validation checks exact registered base bytes, bounded single query keys, no percent-encoded key aliases/duplicates/userinfo/fragment/trailing slash, matching state and issuer, and a still-pending same-generation attempt. It then posts the code and verifier to the exact trusted token route over TLS. This is a first-party adjunct, not a claim of OIDC/OAuth client interoperability.
5. Server atomically consumes code and creates native session/access/refresh rows plus a fixed audit marker, rechecking active account and every binding. Return material only after exact durable readback; a used code cannot mint another family. PKCE proves verifier possession, not app attestation. Public clients have no client secret.
6. Native stores only its own scoped session, using device-only secure storage, backup exclusion and issuer/account namespaces. Access may stay in memory. A late response after sign-out/switch cannot resurrect local authority. Failed/ambiguous code exchange requires a fresh browser attempt, not code replay or browser-cookie fallback.

Synthetic callback registrations are exact `https://callbacks.account-sync.example/{apple-ios|apple-ipados|apple-macos|android-play|android-fdroid}/return`. They are fixture-only claimed-HTTPS shapes, **not** App/Universal Link registrations. Real claimed HTTPS callbacks, Apple associated-domain/team identities, Android asset links/signing channels (including F-Droid), macOS callback delivery and browser fallbacks are unselected mobile/security-owner decisions. Custom schemes/loopback redirects are rejected in this source registry; approving them later requires new registry/vectors. Never reuse `healthmd://cloud/requests` as an auth callback (E07).

The new profile namespace requires account opt-in as well as scope; it grants only configuration. ## Session lifecycle and isolation

- Access/refresh records bind issuer + environment + audience + account + registered client + installation + session family. Before exchange, pending/code records bind issuer/environment/audience/account/client/callback/challenge/scopes; first verified consumption binds the supplied installation label to the family. The initial authorization URL carries no installation ID, so this is not pre-exchange hardware binding. Validate exact token type, expiry, family revocation/account status on **every** call; no offline token cache that ignores account deletion. Wrong service profile or audience denies even if identifiers match.
- Refresh is one transactional compare-and-set: invalidate parent, create one child/access pair and audit marker, then verify durable state. Native serializes refreshes. A second use (including a concurrent legitimate loser) revokes the whole family/access authority; no grace window, replay success or second child. This deliberate availability trade-off needs security/mobile review.
- Lost issuance/refresh response: if the server cannot verify durable state it returns `503 verification_pending` with no secret; client marks authentication uncertain. If commit occurred and the replacement secret was lost, reauthenticate; never resurrect parent or regenerate a secret from hashes. Reuse detection may invalidate the first winner.
- Revoke is idempotent and owner-scoped. Native access can revoke only itself; refresh digest can be recognized on the revoke-only route (including a consumed digest) only to revoke its own family, never refresh or list. Browser recent reauth can revoke any native family owned by that account. A durable revocation/audit proof is required before reporting remote success. Unknown/cross-account target gives the same not-found result.
- Local sign-out immediately fences incoming work and stops sync. Offline remote revocation is shown as **pending**, not complete. An optional encrypted, revocation-only retry record may retain the minimum self-revoke proof until acknowledgement/expiry; it cannot refresh, read config or appear in normal account state. Secure deletion and retry retention require review.
- Account disable/deletion invalidates browser, native families, ingest, request and MCP authority through their own checks. Erasure must eventually cover config revisions, tombstones, pending auth records, refresh history, encrypted caches and portability artifacts under the independently approved config policy. Do not claim existing health-object deletion already implements this new coverage.
- Account/environment switch stops old sync, advances generation, quarantines old pending edits and mapping/cache/outbox, clears normal credentials, and starts a separately consented session. Never replay old-account writes, match profiles by name, auto-link by email/provider, or migrate pilot identities. Existing local copies remain local; publishing them to another account is a new explicit disclosure.
- Sign-out does not delete local profiles, purchases, existing user-configured destinations or pre-existing schedules. It removes account sync authority; future account-dependent execution must pause independently. No sign-out implementation may silently revoke independent ingest/MCP/provider/direct grants or claim it did so.

## Opt-in, bootstrap and safe native apply

1. Account sign-in starts with zero selected profiles and no config transfer. Explicit Sync profiles consent discloses names/templates/endpoint hints, selected profiles, account/environment, encryption/retention policy and separately disabled Health uploads. Consent withdrawal stops transfer; local copies survive unless separately removed.
2. First connect offers **publish selected local**, **adopt selected account**, or **keep both**. No automatic Replace, name-based identity merging, active-profile selection or pre-existing schedule retargeting. Publish allocates cloud IDs without exposing native IDs; adopt allocates native IDs and blocks them with nil bindings/disabled schedules; keep-both makes independent mapping choices. AS05 specifies exact conflict/idempotency receipts.
3. Sync reconciles portable revisions into a local review/candidate store, separate from locally accepted execution snapshots. Never call `activate` or `settings.apply`/`updateExportSettings` as a network side effect (E09/E10). Existing accepted active settings/jobs remain fixed and may continue using their unchanged qualified local authority; fetched content cannot execute on the same cleared native ID. Apply records exact accepted revision/hash and result after a local protected action. Unreadable mapping/sidecar/preservation provenance quarantines writes (E13), including Apple's empty-on-read-failure extension result; it cannot authorize foreign deletions. Preserve recognized foreign/unsupported content through local edit overlays, not just unchanged imports.
4. A new cloud-adopted row must be execution-blocked **before** persistence can expose it; nil bindings cannot fall through to a global destination. Remote destination/schedule changes invalidate approval for that revision. Preserve prior runnable local copy and bound jobs, or atomically block the changed row/disable affected automation before exposing changed intent; AS10 must select/test that transaction. Do not silently overwrite an enabled schedule's live configuration.
5. Local explicit rebind + permission/credential/entitlement/background/cadence checks precede any manual/scheduled/automation/direct execution. Renaming, opening, duplication or editing cannot clear blocks. Do not equate Android's display projection for connected-Mac intent or a low-level confirmation hook with qualified Mac transport.
6. Respect local Configuration Protection when selecting/publishing/applying/editing synchronized content, while allowing read-only review and security sign-out/revocation. It is not a remote auth scope or a security sandbox. Existing schedules and frozen work remain local and are not rewritten by sync.
7. Cloud deletion creates a tombstone, not permission to delete a last/active native profile or kill work invisibly. Quarantine a conflict/offer keep-local/unlink under AS05/AS10 rules. If the local last-profile invariant cannot be preserved, stop apply and report requires-action.

## Sensitive configuration policy seam (not a selected policy)

Persistent adapter must require `ConfigurationPrivacyPolicy` with reviewed version and explicit encryption/key model, current/revision/tombstone/consent/audit/auth-state retention, deletion+backup-expiry behavior, portability, key rotation/recovery, region/processors and operations access. A missing field denies storage/read/apply; no implicit reuse of ADR-0007 unlimited export retention or export/identity/MCP keys. Envelope encryption is a possible reviewed implementation, **not selected**; no end-to-end/zero-knowledge claim. Bind purpose + issuer/env + account + profile + revision/contract identity as authenticated data and prohibit ciphertext swapping regardless of the chosen model. Synthetic adapter uses in-memory sentinels only.

Configuration download/portability requires config authority and bounded exact revision provenance, never bundles health, credentials or native IDs. No anonymous object URL, token/selector in URL, third-party scripts/telemetry, plaintext browser persistence or logging of names/templates/endpoints/account IDs. Security metrics are fixed event enums and bounded coarse counts. Consent withdrawal, account deletion, local unlink and server tombstone are different actions; UI must not claim erasure before verified policy completion.

## Capability classifications and consumer/version analysis

The independent [classification file](../../packages/contracts/account-auth/v1/capability-classifications.json) uses exact `planned`, `shared`, `apple_only`, `android_only`, `unavailable` vocabulary. New optional account sign-in/config sync/local-revision review are **planned on all targets**, with AS03/AS04/AS08/AS09/AS10/AS12 targets, including separate iPad/macOS qualification.
