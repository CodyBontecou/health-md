# Wear OS implementation checklist

The expanded evidence-based audit is maintained in [`wear-os-completion-audit.md`](wear-os-completion-audit.md). It is authoritative for remaining manual, hardware, CI, signing, and Play gates; passing local proxies must not override it.

Health.md for Wear OS is a non-standalone companion. Phone Health Connect is authoritative; the watch performs no Health Connect reads and no Health Services sensing. The private `:wearable-contract` is not an export/direct-protocol change.

## Synchronization and privacy

The phone reads only Steps, Active Calories, Exercise Sessions, Sleep Sessions, Heart Rate, Resting Heart Rate, HRV RMSSD, and Oxygen Saturation permissions that are actually granted. Partial snapshots remain useful and carry a permission-required state. The transfer excludes samples, timestamps below day/capture granularity, source app, record IDs, metadata, routes, errors, and user identity. `DataClient` holds only latest state; `MessageClient` carries payload-free refresh requests, bounded delete ordering controls, and bounded acknowledgements. Normal delivery persists its target-watch inventory before publishing the DataItem, so early ACKs are correlated rather than dropped and unexpected nodes cannot alter aggregate status. Watch storage is atomic state in `noBackupFilesDir`. Failed refreshes retain last-good data. Clear Watch Data is first accepted as a unique durable WorkManager request; only that worker reserves the ordering barrier and persists `REQUESTED`, so process death cannot strand a privacy intent between app preferences and WorkManager. The worker then stores an aggregate-free cleared-through tombstone durably, removes the durable snapshot, and sends the same control to reachable capable watches for immediate deletion. `REQUESTED` → `TOMBSTONE_STORED` → `SNAPSHOT_REMOVED` phases survive cancellation, the WorkRequest carries an idempotency ID for post-completion replay, dedicated startup recovery bypasses Health Connect eligibility, and every ordinary worker/sync finishes a pending clear under the same transaction lock before producing data. Missing immediate acknowledgements remain queued/unconfirmed rather than blocking the durable privacy action; Settings uses the clear transaction’s own targeted/acknowledged counts instead of stale snapshot counts, and the target inventory survives transaction completion so a delayed offline-watch `DELETED` acknowledgement can resolve visible status after reconnect. The tombstone prevents delayed pre-clear delivery from restoring deleted health data and is removed only after a newer durable snapshot is stored. Corrupt watch ordering markers fail closed: measurements are hidden/deleted, compatible payloads remain rejected, and an explicit newer clear re-establishes a valid durable barrier.

Freshness is 0–4 hours current, 4–24 hours stale with age, and over 24 hours hidden. Tiles/complications are local-cache-only and never claim real-time data. Eligible health synchronization cadence is 30 minutes and platform-inexact. If a foreground publication represents aggregates while background Health Connect reads are ineligible, a separate 30-minute WorkManager audit checks only permission names—never records—and publishes an aggregate-free replacement if any represented grant disappears; full eligibility reconciliation cancels that audit once normal synchronization becomes eligible or retained aggregate state is removed. Tiles include local timeline entries for stale-age, 24-hour expiry, and captured-zone midnight transitions in addition to a one-hour host refresh request; complication polling is push-only with native validity/timeline transitions, including cross-midnight hourly stale entries only for bounded Recovery/Sleep/HRV values.

## Release/runbook

1. Keep phone and Wear `versionName` equal; maintain globally unique version codes (phone below 1,000,000; Wear from 1,000,000).
2. Configure the same release keystore in `local.properties` for both modules.
3. Run `./scripts/validate-play-listing.sh`. Initial paired AAB upload must not require Wear screenshots because the exact Play-generated/Play-signed installed build does not exist yet.
4. Run the validation commands below and inspect both AAB manifests with the release keystore environment configured. The validator attests the shared upload-key configuration; the installed Play App Signing certificate remains a credentialed Play Console verification gate because AABs do not embed APK-style signer certificates.
5. Upload both AABs in one edit, assigning phone to `qa` and Wear to `wear:qa`; retain the successful exact-SHA release run ID and its pre-mutation QA upload intent/AAB artifacts; protected ingest later proves the paired upload and credential cleanup steps succeeded. Verify Play generation/signing, install the exact closed-track Wear build, capture and visually approve its physical app/Tile framebuffers, package those artifacts in a protected evidence submission, and dispatch exact-tag `.github/workflows/android-wear-screenshots.yml` with the submission run ID and attempt. Retain its attempt-qualified checksum-covered committed-edit receipt; do not invoke the implementation script locally.
6. Perform and explicitly attest closed-track phone-first and watch-first installs, upgrade from production, upgrade/downgrade skew, and delete/uninstall/reinstall before production. Assemble the complete unsigned/unsealed release evidence root (generated APKs, screenshots/capture receipts and independent visual approval, paired/manual QA, battery controls, and exact push-CI receipt); omit the protected screenshot-upload and QA-upload receipt namespaces. Submit its digest-bound tarball with `android-wear-evidence-submit.yml`; protected `android-wear-evidence.yml` takes the full submission run ID/attempt, QA upload run ID, and successful screenshot workflow run ID/attempt (while separately retaining that workflow's earlier screenshot-source submission run/attempt), validates their provenances, downloads both protected receipts plus the exact QA AABs directly, independently retains the current exact `qa`/`wear:qa` pair, safely extracts submitted evidence, creates the checksum/HMAC seal, verifies all artifacts, and retains a SHA/version-bound artifact. Provide that successful ingest run ID to promotion. Promotion revalidates it before obtaining the production-only Play credential, retains an immutable intent, independently compares committed Play screenshot hashes to the sealed assets, and then requires one newly committed paired edit to `production` and `wear:production`. It fails rather than treating an already-partial/full pair as proof. If only post-commit receipt retention fails, the protected recovery-only workflow proves the original paired-edit step succeeded and re-queries the sealed evidence/current Play state without mutating tracks. Never place Wear on a default phone track or promote only one artifact when its contract version changed.

## Physical battery/OEM QA gate

On Pixel Watch and one Samsung Galaxy Watch (small and large round devices), run a 24-hour paired test and a 12-hour disconnected test. Record baseline/control and Health.md battery deltas; fail if Health.md exceeds 2% watch battery/24h without user refresh or causes wake-lock/ANR evidence. Use `scripts/capture-wear-battery-evidence.sh` at baseline start/end and Health.md start/end so every checkpoint retains raw watch-feature, explicit round-display/physical-size, build-characteristics, hardware/qemu/virtual-device checks, model/build, standard AC/USB/wireless charge state, level, exact package/version, installed Play-generated base APK digest and signer, package UID, package-scoped batterystats, power, alarms, jobs, logcat, independent reviewer/ticket, one invariant control-profile ID, and controlled-condition/no-user-refresh/no-wakelock-ANR attestations with checksums; the script rejects plugged/unknown charge state and does not reset or mutate device state. Keep comparable brightness, radios, watch face, complications, ambient settings, activity, and starting charge in the protected manual record represented by that control-profile ID. Exercise: phone absent/unreachable/reconnect, Bluetooth-to-Wi-Fi relay, reboot, locale and timezone changes, 1.3×/largest font, TalkBack, RTL Arabic, ambient/off-wrist, revoked/partial Health Connect permissions, corrupt/duplicate/out-of-order payloads, clear data, Tiles, every complication type, and uninstall/reinstall. Confirm no health payload in logcat, backups, analytics, or crash breadcrumbs.

Example checkpoint (repeat for all four checkpoints, both scenarios, and both OEMs):

```bash
EXPECTED_WEAR_APK_SHA256=<approved-play-base-apk-sha256> \
EXPECTED_PLAY_APP_SIGNING_CERT_SHA256=<authorized-play-signing-cert-sha256> \
EXPECTED_WEAR_VERSION_CODE=1000030 EXPECTED_VERSION_NAME=1.8.1 \
REVIEWER_ID=<independent-reviewer> REVIEW_TICKET=<approval-record> \
CONTROL_PROFILE_ID=wear-battery-profile-v1 \
CONFIRM_CONTROLLED_CONDITIONS=yes CONFIRM_NO_USER_REFRESH=yes \
CONFIRM_NO_WAKELOCK_ANR=yes ANDROID_SERIAL=<watch-serial> \
scripts/capture-wear-battery-evidence.sh \
  .pi/evidence/wear-battery/pixel/paired-24h/healthmd-start \
  pixel "Pixel Watch model" paired-24h healthmd-start
```

Treat battery percentage as a coarse user-facing measurement and use the captured package-scoped batterystats/power evidence to investigate any regression or inexplicable delta. After all sixteen checkpoints exist (four checkpoints × two scenarios × two OEMs), run `python3 scripts/verify-wear-battery-evidence.py <evidence-root> --wear-apk-sha256 <play-base-apk-sha256> --play-signer-sha256 <authorized-play-signer-sha256> --wear-version-code <exact-code> --version-name <exact-version> --expected-reviewer <protected-reviewer> --expected-review-ticket <protected-ticket> --expected-control-profile <protected-profile> --report <evidence-root>/verified-report.json`. It verifies every exact checksum inventory, exact Play APK/signer binding, identity/build/reviewer/control-profile comparability, ordered non-overlapping checkpoints, comparable starting charge, minimum 24h/12h durations, no app-attributed active wake lock at capture, scoped crash/ANR and log-payload checks, a prefix-stable batterystats event stream with no charging event between endpoints (while ignoring mutable dumpsys headers), and the baseline-subtracted ≤2%/24h threshold. The release preflight executes the same validator. Do not pass this gate using emulator output, a static manifest review, or missing control measurements.

## Physical paired Data Layer QA evidence

At each manually reached checkpoint (`installed`, `synced`, `offline`, `reconnected`, `cleared`, `rebooted`, `final`), capture both devices without mutating their state:

```bash
EXPECTED_PHONE_APK_SHA256=<approved-play-base-apk-sha256> \
EXPECTED_WEAR_APK_SHA256=<approved-play-base-apk-sha256> \
EXPECTED_PHONE_VERSION_CODE=30 EXPECTED_WEAR_VERSION_CODE=1000030 \
EXPECTED_VERSION_NAME=1.8.1 \
EXPECTED_PLAY_APP_SIGNING_CERT_SHA256=<authorized-play-signing-cert-sha256> \
REVIEWER_ID=<independent-reviewer> REVIEW_TICKET=<approval-record> \
scripts/capture-wear-paired-qa-evidence.sh \
  .pi/evidence/wear-paired/pixel/synced \
  <phone-adb-serial> <watch-adb-serial> pixel synced
```

The collector fails unless the exact phone 29 / Wear 1,000,029 pair is installed, each installed base APK matches its approved digest, both certificates match the separately authorized Play App Signing SHA-256, and an independent reviewer/ticket identifies the protected manual action/result record. It retains pulled base APKs plus `apksigner` certificate output and package/services/connectivity/battery/logcat state. For the non-debuggable Play release it queries a release-safe `android.permission.DUMP`-protected diagnostic provider that returns only cache presence/size/SHA-256 and ordering-marker booleans—never health values or JSON. It rejects contract-field log leakage and crash/ANR evidence and checksums every output. After all seven checkpoints exist for both OEMs, run `python3 scripts/verify-wear-paired-qa-evidence.py .pi/evidence/wear-paired --phone-version-code <exact-phone-code> --wear-version-code <exact-wear-code> --version-name <exact-version>`; release preflight executes the same validator and checks checksum coverage, OEM/device/build/artifact/signer continuity, chronological checkpoints, durable cache across sync/offline/reconnect/reboot, cache hash continuity while offline, a newer durable hash after reconnect, reboot persistence, no mismatch markers, and a cache-free clear with a durable barrier. The manual record must separately identify the action and visible expected result: initial Data Layer delivery/ACK, watch refresh completion only after a newer sequence, disconnected last-good rendering, queued reconnect delivery, Clear Watch Data removal and DELETED ACK, reboot persistence, timezone/skew behavior, and all host-rendered Tiles/complications. Do not infer a real round trip from unit tests or cache injection.

## Validation

```bash
ANDROID_HOME=$HOME/Library/Android/sdk ./gradlew :wearable-contract:test :wear:testDebugUnitTest
ANDROID_HOME=$HOME/Library/Android/sdk ./gradlew :wear:lintDebug :wear:assembleDebug
ANDROID_HOME=$HOME/Library/Android/sdk ./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
ANDROID_HOME=$HOME/Library/Android/sdk ./gradlew :wear:bundleRelease :app:bundleRelease
RELEASE_STORE_FILE=/path/to/release.jks \
RELEASE_STORE_PASSWORD=... RELEASE_KEY_ALIAS=... RELEASE_KEY_PASSWORD=... \
WEAR_REQUIRE_SIGNING_ATTESTATION=true \
./scripts/validate-wear-artifact.sh \
  wear/build/outputs/bundle/release/wear-release.aab \
  app/build/outputs/bundle/release/app-release.aab
```

Post-upload Play signer evidence is captured read-only with `scripts/capture-google-play-generated-apk-evidence.sh`. It requires exact expected phone/Wear version codes and semantic version name plus an independently authorized Play signing certificate SHA-256, downloads the exact generated phone/Wear base-master split APKs used as installed `base.apk`, verifies package/version and actual APK certificates, and retains the exact bytes plus raw inventories and checksums in a non-overwritable evidence set. Both collector and release preflight run `verify-google-play-generated-apk-evidence.sh` so the receipt is rebound to those bytes and authorized signing-key group instead of being trusted as self-attested JSON. No Play edit is created.

The API 34 x86_64 Wear emulator smoke gate is defined in `.github/workflows/android-ci.yml`. After an authorized push and successful run from a clean immutable HEAD, retain a bound receipt with `scripts/capture-wear-remote-ci-evidence.sh <run-id-or-url>`; it verifies the workflow SHA, Wear job, and aggregate Android CI gate before writing `.pi/evidence/wear-ci/verified-run.json`. The preflight rejects missing or malformed receipts. API 34 is the latest standard `android-wear` image supported by that runner; newer Wear packages use extension/signed package identifiers. `scripts/run-wear-emulator-smoke.sh` derives the package, semantic version, Wear code, and SDK identity from the inspected APK with `aapt`, cross-checks the installed package rather than pinning the current release, and verifies install, launch, all 12 surface components, setup/fresh/partial/stale/expired/unavailable/version-mismatch and recovery dashboard states from the production durable cache (including force-stop/offline relaunch), aggregate rendering and mismatch value suppression, touch scrolling, required real-encoder discovery plus injected rotary scrolling, 1.3× font smoke, packaged Arabic RTL resources and relaunch, disabled packaged backup, no-backup cache location, no aggregate-field/value leakage in app-run logcat, and absence of Health.md crash/ANR. A matching API 34 ARM64 small-round run passed locally with rotary enabled; session evidence is retained under ignored `.pi/evidence/wear-emulator/`. Physical QA requires actual paired watches and is never inferred from an emulator.
