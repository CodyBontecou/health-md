# AS07 read-view collector — inactive TypeScript SOURCE

`src/profile-sync-v1-read-view.ts` collects one bounded AS05 read view in factory-local memory. It is not full reconciliation, authenticated server completeness, private durable storage, a working sync client, or native acceptance. AS07 remains incomplete/blocked. There is no installed router, HTTP handler, Worker binding, network acquisition, health port, credential, native apply, mapping, outbox, journal, conflict resolution or deletion implementation.

Governing surfaces: [source design](../../../docs/architecture/account-profile-sync-source-design.md), [AS05 contract](../../../packages/contracts/profile-sync/v1/contract.md), [ADR-0007](../../../docs/architecture/adr-0007-healthmd-cloud.md) and [proposed ADR-0008](../../../docs/architecture/adr-0008-multi-user-healthmd-cloud-production.md). No wire/schema/registry/fixture change or mobile capability claim is made. The Python SOURCE, RAM authority, AS02, native branches and existing service profiles remain independent and unchanged.

## Admission and public seam

The only entry is `createProfileSyncV1ReadView`. No injection returns fixed `unavailable` for every method and a frozen empty diagnostic. It does not inspect input bytes or invoke parsing, crypto or a timing hook. Factories share no mutable state.

Explicit injection requires `healthmd.profile-sync.v1.read-view.synthetic-only` and an owned, closed context `{ issuer, environment, account, generation }`. Issuer is exactly `https://issuer-a.account-sync.example` or issuer-b; environment is synthetic-a/b; account is sentinel-A/B; generation is a nonnegative safe integer. These independent reserved values mirror Python SOURCE. They are synthetic admission/provenance and cancellation, never a principal, account consent, real issuer policy or execution authority. Invalid admission stays unavailable.

- `select(context, originalReadBytes)` uses actual `parseProfileSyncV1Read`. Revision selectors are refused as `invalid`, not interpreted as latest head. A new view starts at null cursor; continuation must select exactly the staged next cursor and mode. Changes need a completed snapshot-derived baseline under exactly the current context/generation, including after a same-partition switch. The collector never manufactures a request or cursor.
- `receive(context, originalReadBytes, originalReplyBytes)` owns both byte ranges before any await. Correlation requires the exact selected request, not JSON-equivalent reserialization. Actual `parseProfileSyncV1Page` validates every record/content/hash. On page failure actual `parseProfileSyncV1Error` may recognize a closed fixed error; it cannot promote content. Optional `waitForParse(completion)` is timing only. Publication independently awaits the real parse AND timing outcome, then rechecks the captured epoch/selection/context.
- `reset(context)` explicitly discards tentative/selected/current parsing state and advances the control epoch. It preserves all original committed records/pages/provenance and requires a fresh snapshot. A new selected snapshot may reuse the original null-cursor request bytes after reset.
- `switch(nextContext)` owns a valid strictly higher generation, fences current work, and requires a new snapshot. The retained committed context is never relabelled. Old context/generation cannot authorize changes under the new context.

Only a consistent final page replaces `committed`; a nonfinal page only extends `tentative`. Empty completed snapshots are valid. Incomplete empty pages are rejected by the real codec. A committed changes view contains the collected events, not a merged live-profile inventory; its high-watermark can constrain a later explicitly selected view. No missingness/deletion decision is made from either collection.

## Retries and fail-closed behavior

Stored exact request/reply pairs are immutable. Exact retries before/after completion return `unchanged` without control/retention changes. A changed reply, including outer whitespace only, is quarantined, never substituted. A duplicate of the currently parsing pair returns `pending`; a different reply to that active request discards the stage and fences both contenders.

Stored requests identify retries, not fresh rounds: repeating a stored exact selector is `unchanged`. A fresh snapshot using identical request bytes needs explicit reset. A differently encoded/limited valid request can explicitly start a subsequent changes view; this bounded collector does not provide a general repeated-round/transport lifecycle. Duplicate recognition covers the currently retained committed and tentative pages only, not an unbounded historical receipt archive. Reset intentionally retires the old committed view's retry eligibility until a fresh view completes. Wire selectors alone cannot distinguish an unsolicited old reply with the same bytes/context from a newly selected request: authenticated transport/cursor binding remains separate.

Invalid read grammar/revision, wrong context, unselected/mismatched request, wrong requested cursor/mode and changed stored retries leave retained state unchanged. A codec-invalid reply to the current selection or an invalid timing outcome discards tentative/selected state, returns `invalid`, and requires snapshot. Current-page view/mode/watermark/order/ID/event/cursor contradictions return `quarantined` with the same discard; the original committed view survives. Late captured work after reset/switch/discard cannot mutate the fresh winner.

Actual fixed `resync_required` discards the stage; `requires_upgrade` discards as `invalid`. Other fixed errors retain the prior selection/stage without saving the error reply or advancing a cursor: unavailable/invalid/quota_exceeded map directly; the remaining non-success results map to `quarantined`. Results contain only the fixed `result` enum, with no reflected fields, exception text or identifiers.

Across all pages, mode/snapshot ID/high-watermark stay fixed; next cursors cannot revisit any already selected cursor. Requested limits are enforced. Snapshot profile IDs are globally unique and rows remain in ascending `(order_key, profile_id)` order; snapshot event sequences are unique even when row order differs from event order. Changes are strictly forward from the baseline and across page boundaries. Repeated IDs are valid only with forward object/event generations, no resurrection after an observed tombstone, and consistent immutable content generations/exact bytes. Unchanged content requires a metadata reorder; new content generations cannot silently describe identical content. Checks use the current collected events and records retained in the immediately previous completed view. They do not reconstruct all historic heads/retired IDs, authenticate completeness, prove contiguous server events or reconcile arbitrary arrival ordering.

## Ownership, observer and SOURCE bounds

Validated AS05 records/content remain their actual immutable branded instances. The exact nested `content_json`, including whitespace/Unicode/LF, is preserved; changed-but-valid registry evidence remains `registry_review` rather than rewritten. Original outer replies are retained separately, never JSON-rebuilt for storage. Requests/replies are frozen readonly number arrays, not mutable exposed typed arrays. SharedArrayBuffer-backed inputs are rejected; ordinary input subranges are copied.

`view()` is detached and deeply frozen: context; committed/tentative contexts, modes, snapshot IDs, watermarks, baseline watermarks, records, original page bytes/selectors and first-selection epochs; next cursor; selected and current parsing bytes/context/selector/epoch; requiresSnapshot; control epoch; retainedBytes and retainedPairs. Immutable branded records may be shared safely; diagnostic objects/arrays are detached. This observer contains potentially sensitive portable configuration and is NOT a log/telemetry surface. Retained old-owner committed data is provenance, not current acceptance.

Limits are SOURCE choices, not product quotas/privacy retention:

- 100 items per snapshot; 256 events per changes view;
- 256 retained distinct page pairs across committed + tentative + current parsing;
- 4,194,304 retained original request/reply bytes across those views plus selected state;
- 8,192 bytes per read; 4,194,304 bytes per individual reply.

A selected request referenced by current parsing/the eventual page is charged once, not twice. Duplicate retries add no retention. Diagnostics detached into caller ownership are not retained factory storage. Codec copies and cancelled asynchronous call frames are transient, not a persistent collector queue; these limits do not claim a bound on all runtime heap/crypto allocations. Bounds are checked before retaining/publishing. Exhaustion returns quota_exceeded with the entire prior observer intact, including tentative/selected state; no prior committed view is deleted to admit a page, even a final page. Explicit reset can release tentative bytes but never increases a quota or removes committed data. No OS restart/durability/recovery claim follows from memory ownership or timing fences.

## Verification boundary

`test/profile-sync-v1-read-view.test.ts` exercises only this module's public seam with actual AS05 codecs and literal Apple1 bytes. Positive two-page snapshot/retry/changes/reorder/tombstone reachability precedes negative coherence/fencing/bounds scenarios. Observer comparisons include public getters, complete nested content, original bytes and control fields, not hashes/call counts alone. Large byte arrays use an allocation-bounded, byte-for-byte comparison while all other fields retain deep comparison. Byte capture preallocates the known wire length; detached byte diagnostics use exact-length copies. Timing gates have no sleeps, polling or success substitute. Input-only hashing creates malformed/future wire cases; expected outcomes come from literals/spec/prior public state.

Parsing diagnostics intentionally become visible before publication, including the owned request/reply and their retention charge. Committed and tentative views remain unchanged until parsing and the timing fence settle. Tests compare that complete observation explicitly, and fence both valid and invalid real-parser work by resetting or switching immediately after `receive`, before its first asynchronous parse can settle, as well as after parsing at the timing hook.

Strict existing Cloud tsconfig plus the new test and unchanged account-auth-v1, profile-sync-v1-contract, profile-sync-v1-ram and service-profiles tests are the intended local proof surface. Actual executions/failures/resource stops are recorded in the bounded wave report, not implied by this document. No audit/dry-run/full-component, native Swift/Kotlin/core, server/OS durability, physical/UI/accessibility, privacy/issuer/key/retention/AS18, rollout or production gate is satisfied here. Default zero ports and sentinels are not proof that a future authenticated/native application is safe.
