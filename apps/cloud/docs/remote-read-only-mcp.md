# Owner-operated retained-export MCP pilot

**Live endpoint:** `https://mcp.healthmd.app/mcp` (Streamable HTTP, `POST` only). This is an explicitly **unbacked, single-user, disposable** pilot, not a durable or independently audited health-data service. The owner accepts permanent loss of this VM's exports and keys. The endpoint is publicly reachable and a separate **aggregate-only Muse credential** was issued after the owner's explicit consent to Muse's default Meta data handling. A new, separately issued `full_export` Muse credential now exists after broader explicit owner consent; whether Muse completed its custom-connector capture is not yet verified. No Grokbot credential exists. Existing aggregate tokens must never silently gain full-export scope.

The original iPhone export writer stays on the **tailnet-only** `:18788` service, the synthetic upload-disabled preview stays on `:18787`, and the unrelated tailnet `:443` service remains unchanged. A new, separately tunneled **write-only** compatibility-export ingress lives at `https://api.healthmd.app/api/v1/exports` and shares the owner's encrypted writer store; it exposes no MCP, dashboard, account or download route. The MCP reader remains a different credential and process, never a route on either writer or dashboard. The static website does not proxy health data.

## Process and authority boundary

- `healthmd-cloud-personal-mvp.service`: writer user `healthmd-cloud`, private source/password/identity keys, encrypted export objects, owner-only tailnet listener. Its database, WAL/SHM and ciphertext files are group-readable by the **dedicated** `healthmd-cloud-read` group, never group-writable; new files inherit that group from setgid data directories. The rest of its source and writer secrets stay inaccessible to the reader.
- `healthmd-cloud-mcp.service`: distinct `healthmd-mcp` user, only the read group and export-decryption keyring in `/etc/healthmd-cloud-mcp/reader.env`; SQLite opened `readOnly` with `query_only`, application objects read from a **read-only systemd mount**, no writer identity key, password pepper or ingest token. It listens only on `127.0.0.1:18789` and requires a separate `hmd_read_…` Bearer credential on **every** request, checking revocation and active account at request time.
- `healthmd-mcp-proxy.service`: `www-data` nginx, no data-directory or secret access, only `POST /mcp` on `127.0.0.1:18790`. It supplies the expected host/proto headers, bounds request size, disables access logs and returns `Cache-Control: no-store`. Other paths/hosts are rejected.
- `healthmd-mcp-tunnel.service`: separate `healthmd-tunnel` user, local-managed Cloudflare Tunnel with credentials in `/etc/healthmd-cloud-mcp-tunnel` (root-owned, group-readable only by that user). An **explicit**, proxied `mcp.healthmd.app` CNAME points only to this Tunnel. Its ingress matches the exact `/mcp` path and otherwise returns 404. Cloudflare terminates public TLS and sees authorized requests; this is not end-to-end encryption from the model provider.

The existing `hmd_ing_…` export token, dashboard password and browser cookies **cannot** authenticate MCP. The offline token-administration CLI and the owner's password-confirmed dashboard run with writer authority; the MCP process contains no account/token mutation tools, write operations, arbitrary SQL or arbitrary filesystem path access. The owner-only dashboard is now publicly reachable at `https://account.healthmd.app/dashboard` through its own Tunnel and HTTPS hostname, with password sessions and no public signup. It is not an MCP or upload route; the read-only MCP process remains separately privileged. The `healthmd.app/dashboard` website redirect is pending protected-main website release. A separately scoped full-export credential can navigate original account-owned retained JSON envelopes and exact byte pages; see [mcp-full-export-tools.md](mcp-full-export-tools.md). Only issue one read token per agent **after** identifying that product, its bearer-header support, retention terms and the owner's consent. A client requiring OAuth rather than a protected per-host Bearer header needs a separate connector; never place a token in a URL.

## Data returned and limits

The original six aggregate tools expose only selected numeric **Apple iOS v8 daily aggregates** using shared metric-registry IDs and units. Android v4 and unverified aliases are not projected into those metrics. The reader verifies owner scope, active account, record date/index/schema, object authentication and plaintext digest before projecting. Provider sidecars, source archives, record UUIDs, raw time series and free text are not returned **by aggregate tools or old credentials**. Explicit `full_export` tokens add five tools for all original retained iOS/Android compatibility JSON envelope fields including those sensitive values, with bounded JSON Pointer and exact-byte pagination; no Android-to-Apple metric alias is implied. Sleep duration is converted from source seconds to registry hours. Results carry civil date, calendar timezone and `timestamp: null`—never an invented instant. Missing days/metrics are omitted, not zero-filled. Aggregate selection filters current snapshots to reviewed iOS v8 records in API envelopes v1/v2 before applying read/catalog limits; Android v4/v5, legacy Apple daily schemas and unknown profiles do not break unrelated supported days or consume their catalog slots. An unsupported current day is omitted, not replaced by an older Apple revision. `missingDates` means no supported aggregate summary, not proof that no envelope was uploaded; full-export inventory and date lookup still discover unsupported snapshots. Integrity failures in selected supported exports continue to fail closed. `heart_rate` is **not** an alias of `heart_rate_avg`.

Six aggregate tools: `health_list_metrics` (latest 365 supported current daily snapshots), `health_get_latest`, `health_get_range` (at most 31 inclusive dates), `health_get_daily_summary`, `health_get_weekly_summary` (seven days with gaps), `health_search` (catalog names/categories only, up to 14 days). Five additional full-export tools: `health_export_guide`, `health_list_exports`, `health_find_export_for_date`, `health_read_export_node`, `health_read_export_bytes`. Discover all historical envelopes including retained supplements (labeled `retentionRole: supplemental`, never merged into primary daily aggregates), follow JSON Pointers/child pages, and concatenate at most 8192 exact JSON bytes per byte page. Full details, privacy risks and navigation examples: [mcp-full-export-tools.md](mcp-full-export-tools.md). Request body <=64 KiB, tool result <=16 KiB, total ciphertext reads <=64 MiB/call, <=60 requests/minute/token, <=2 concurrent requests. Oversized/broad requests fail, never silently truncate. Health-free audit logs contain only pseudonymous token digest prefix, tool name, status and duration—not arguments, dates, health values, credentials or raw identifiers.

## Token administration (offline operator alternative)

From a shell on the VM **after owner consent for the specific agent**:

```sh
GID=$(getent group healthmd-cloud-read | cut -d: -f3)
sudo -u healthmd-cloud -g healthmd-cloud env HEALTHMD_VM_READER_GID="$GID" /opt/healthmd-cloud-mvp/bin/node --env-file=/etc/healthmd-cloud-mvp/secrets.env /var/lib/healthmd-cloud-mvp/source/mcp-admin.mjs create --user=owner --label=AgentName --days=90 --scope=aggregates
# Explicit owner-authorized full export: use --scope=full_export instead.
sudo -u healthmd-cloud -g healthmd-cloud env HEALTHMD_VM_READER_GID="$GID" /opt/healthmd-cloud-mvp/bin/node --env-file=/etc/healthmd-cloud-mvp/secrets.env /var/lib/healthmd-cloud-mvp/source/mcp-admin.mjs list --user=owner
sudo -u healthmd-cloud -g healthmd-cloud env HEALTHMD_VM_READER_GID="$GID" /opt/healthmd-cloud-mvp/bin/node --env-file=/etc/healthmd-cloud-mvp/secrets.env /var/lib/healthmd-cloud-mvp/source/mcp-admin.mjs revoke --id=<token-id-from-list>
```

Offline CLI tokens are shown **once**, stored only as hashes, default to 90 days and expire in at most 365 days. The owner dashboard (also available on the separate password-protected `account.healthmd.app` origin) issues only explicitly consented `full_export` tokens after password re-entry, for 1–90 days, and can list/revoke existing owner-scoped credentials. Do not issue an agent token in a shared pane, source file, issue, CI or chat. Rotate by issuing a new token, updating the approved client's secret store and revoking the old token. Tokens default to `aggregates`, including all previously issued credentials; they allow the eleven-metric catalog and no full-export tools. A newly issued `--scope=full_export` token can traverse **all** retained JSON data for that account (including sensitive free text, identifiers and embedded base64 binary) within per-call bounds. No per-metric grants or user-facing step-up prompts exist; do not infer that an aggregate-only token consents to a scope upgrade.

A compatible remote MCP client registers the URL `https://mcp.healthmd.app/mcp`, and stores its private token as an `Authorization: Bearer <hmd_read_…>` header in the client's secret store. Use normal `Content-Type: application/json` and `Accept: application/json, text/event-stream`. The server responds with JSON. Muse described a custom VM connector that stores a Bearer header in its Secure Vault, but its actual connection has not been independently verified. Muse default conversation handling was disclosed to and accepted by the owner; Meta may review and use tool results for training, and no retention period was established. Grokbot client/retention remains unqualified. Cloudflare currently blocks the generic `Python-urllib` user agent with HTTP 403 even before MCP auth; ordinary curl, Node fetch and a named client user agent passed public tests. Verify a proposed client rather than assuming interoperability.

## Operation and rollback

Services are enabled for reboot: `healthmd-cloud-personal-mvp.service` (writer), `healthmd-cloud-mcp.service`, `healthmd-mcp-proxy.service`, `healthmd-mcp-tunnel.service`. The writer received migration `0005_mcp_read_tokens.sql` in a stopped-writer maintenance window; migration `0006_mcp_read_scope.sql` was subsequently checked and applied in a controlled writer restart before the scoped reader was activated; SQLite integrity and continued `/health` behavior passed. The reader's mount was verified read-only, its distinct UID could read but not write data, and could not read writer secrets/source or signal the writer. Public tests exercised valid temporary owner credentials, denied missing/write-only/invalid/revoked credentials, verified all six read tools and no-store behavior, then **revoked the temporary token and deleted its delivery copy**. The owner authorized a 30-day aggregate-only Muse token and later a separate 30-day full-export Muse token; both are active unless revoked/expired. The original remains aggregate-only until it can be revoked after confirmed Muse Secure Vault rotation. No Grokbot token has been issued. Updated rollout evidence is in [mcp-public-readiness.md](mcp-public-readiness.md).

To cut off ingress immediately without affecting the iPhone writer or unrelated ports, run `sudo systemctl stop healthmd-mcp-tunnel.service` and disable its autostart until resolved. The explicit DNS record is tracked privately at `/etc/healthmd-cloud-mcp-tunnel/dns-record.json`; delete it only after verifying it still targets this Tunnel. For token compromise, revoke that token offline and verify it returns 401. Never delete `/var/lib/healthmd-cloud-mvp/data` or historical export keys while retaining exports. **There is no off-host backup, password reset or key recovery**; rollback of code/service settings does not guarantee recovery from data corruption or VM loss.
