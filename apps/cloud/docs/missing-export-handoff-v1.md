# Missing-export handoff v1 — design, not deployed

**Status:** proposed; no deep link or mobile request receiver exists yet. Single-owner, unbacked pilot only. A dashboard request is not evidence that a reading exists on the phone, was authorized by HealthKit/Health Connect, or was successfully uploaded. Do not display a working link or a successful repair until both native apps and server verification are shipped and tested.

## User outcome and defaults

From the authenticated account's retained-export explorer, choose exact owner-calendar dates and reviewed source-specific metric IDs, or **entire selected days**, plus Summary, Detailed Time-Series, or Lossless Health Records where the platform supports that detail. Inspect the estimated scope, source, coverage uncertainty and potential replacement consequences. Create a short-lived queued request and open Health.md with a **static** app link (no health dates, metric names, account identifiers, request IDs, tokens or endpoint values in the URL). On a separately enrolled phone, fetch the scoped work over TLS, show an in-app review, and require the user to confirm before querying the OS or uploading. Use only the already configured, exact Health.md Cloud HTTPS endpoint and that account's write-only token from the native secure store. Never change the saved endpoint, token, metric settings, schedules or export profiles as a side effect. Never fetch retained exports with the write-only token.

Account dashboard evidence states: `not_uploaded` means no current snapshot; `value_unavailable_in_uploaded_summary` means a reviewed projection has no verified value in the current envelope, **not** that the device has a reading or that the metric was excluded by the app; `unsupported_profile` and `read_limit` are not candidate measurements. A captured zero is not missing. A partial/failed manifest requires separate inspection, not a zero. Different iOS/Android statistics must retain distinct identities (e.g. HRV SDNN versus RMSSD). Date selection uses logical owner days in the source calendar time zone; the native review must show/verify the actual day boundary and reject mismatched source/platform/calendar rather than silently change it. When no trusted zone is present, request mobile confirmation; do not infer it from the web browser.

## Snapshot safety — prerequisite for metric-specific repairs

Current `healthmd.api_export` ingestion replaces the *current daily pointer* with the latest accepted envelope for that date; it retains old envelopes as revisions. A metric-only re-export for an already uploaded day would therefore hide every previously uploaded field not repeated in the new snapshot (including providers, time series and archives). **Do not implement metric-specific repair by sending an ordinary partial API export and letting it replace that pointer.**

V1 may allow exact selected metrics on a day with no current snapshot. For an already uploaded day, use a separate, authenticated **supplemental receipt** that stores its original compatibility envelope as an additional encrypted retained export, binds the exact requested metric IDs and owner date to that envelope, and does not replace the primary `daily_records` pointer. A future reviewed read model can present primary and supplemental values side by side, or select the latest metric-specific evidence with explicit per-field provenance; it must never pretend it is a complete daily snapshot or merge archives/profiles without reviewed semantics. An alternative full-day refresh is allowed only as a separate, explicitly confirmed replacement request after the phone shows its actual metric/detail/provider scope and warns that a newer complete snapshot can legitimately change or remove previously reported values. Failure to guarantee the supplemental/non-replacement path is a **blocker to enabling links for existing dates**. The mobile exporter must not mutate a saved profile to carry an ad hoc request.

## Proposed handoff and authority

1. Account session + same-origin browser intent creates a bounded request (maximum 31 logical days per draft; metric IDs must be source-reviewed; a single source/platform per request; detail level explicit). Encrypt its dates, metrics, zone and mode at rest using a purpose-separated authenticated key, account ID and request ID as associated data. D1 stores only owner/device binding, state, expiry and ciphertext metadata. Default expiry 15 minutes for a pending launch and a separately bounded lifetime for an accepted upload. Enforce single-owner quota, deduplicate exact request IDs, and allow cancellation; account deletion removes requests and enrolled devices. Never put the request body in logs, analytics, browser storage or a URL.
2. Phone enrollment is a separate, revocable, **request-only** grant, not an ingest token, MCP reader token, account cookie, or general export reader. App initiates a rate-limited short-code enrollment and keeps a generated credential only in Keychain/Android Keystore-backed storage; account owner confirms the code and device identity in the account session with password step-up. Authenticate every device poll, claim and status receipt. An unenrolled phone or a revoked grant learns nothing about queued scopes. Store only a token hash (or device public key) server-side; never embed it in a link or return retained export payloads to the device grant.
3. Dashboard queues to an explicit enrolled device. A static `healthmd://cloud/requests` (or reviewed platform-equivalent app link) only opens the app. A link by itself conveys **zero** authorization or request selectors and cannot start an export. The app fetches only that device's pending request from the account origin via its scoped grant; the public write-only API and public read-only MCP origins must not serve request reads. Limit claim to one device, protect against duplicate launches/replay/expiry, and expose no health payloads to link resolvers or browser referrers.
4. Native review presents source, exact dates/zone, metric IDs or entire-day selection, detail, estimated volume, existing-day supplemental vs full replacement, destination host, and possible permission/size limits. User must explicitly tap **Export**. If endpoint is not the exact approved `https://api.healthmd.app/api/v1/exports`, or there is no matching stored write-only credential, stop with setup instructions. Do not auto-install a credential, broaden permissions, start a schedule, substitute a tailnet URL or use a different endpoint.
5. Capture and upload through the production API Endpoint runner with immutable per-action scope/destination, existing bounded batches and normal OS permission/lifecycle rules. The public ingest origin may accept a purpose-specific request correlation header *in addition to* the write-only token, but the header is not authority: bind it to the token's account, approved request, selected source and exact day scope at commit time. For supplemental days, ensure transactionally that upload does **not** overwrite the current daily pointer. Do not retrofit historical envelope bytes; this is server-internal metadata/projection versioning. Sidecar-only, no-data, permission denial, failed dates, 413, cancellations and partial batches have distinct receipts.
6. Show a per-day/per-metric outcome only after correlating server-accepted envelopes and their evidence to the request. Phone-reported completion without a verified server receipt is `unverified`, never `uploaded`. A successful upload may still contain no measurement. Inventories, download, explorer and full-export MCP remain owner-scoped and provenance-aware; older and supplemental envelopes remain navigable. Deletion/retention/quota/reconciliation cover the new objects, and all responses are no-store.

## Product scope and version decisions

The request grammar and device-grant transport need a versioned, language-neutral contract and synthetic Swift/Kotlin/TypeScript conformance fixtures **before** enabling the new link. The existing Apple daily v8, Android v4/v5, `healthmd.api_export` v1/v2 compatibility bodies and direct protocol v3 stay byte-identical unless a reviewed producer requirement makes a new platform/profile version necessary. This plan does not claim a common public health-data schema change or direct live-iPhone access by the dashboard. Android Raw API Snapshot NDJSON is not accepted by the Cloud receiver. Exact native metric mappings, detail availability and approved selected-date batching must be checked against both platforms; classify any genuine platform-only ability in `packages/contracts/product-capabilities.json`. The CLI and Obsidian plugin remain consumers of original exports, not silent merged repairs.

## Delivery sequence and stop gates

1. Define contract, native metric allowlists, owner-day/zone fixtures, and snapshot-safety cases; qualify the supplemental storage/read model with synthetic revisions. Reject unsafe narrow requests for already-uploaded days until that model is proven.
2. Add account-only encrypted draft/preview/expiry/cancel and device approval/revocation with migrations. Test cross-owner and cross-device isolation, invalid CSRF, stale claims, token separation, quota/expiry, and ingress denial. No live credentials or health data in tests or logs.
3. Add native deep-link handling and enrollment/review on **iOS and Android** using existing exporters and secure stores. Test unsolicited/duplicate links, refusal, lost/locked phone, changed endpoint, missing credentials/permissions, source mismatch, process death and batch interruption. An unapproved link must not call HealthKit/Health Connect or send any request.
4. Add ingest correlation and receipts with transactional provenance. Test both existing-date supplements and absent-day snapshots, one-day partial/empty outcomes and rollback/retry without duplication. Run affected Apple, Android, contract, cloud, CLI/consumer gates. Physical iPhone and Android device QA must verify confirmation and exact destination before announcing a working link.
5. Only then show and deploy the launch link. Preserve tailnet writer :18788, upload-disabled preview :18787, public write-only API, separate account origin and MCP, and unrelated routes. No public signup or durability claim. If any gate is unavailable, leave links disabled and report the blocker rather than ship an apparent one-tap export.
