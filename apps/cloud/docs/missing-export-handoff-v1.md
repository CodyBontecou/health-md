# Missing-export handoff v1 — staged, not deployed

**Status:** backend draft/preview UI implemented at `/repair`. A strict static-link detector is staged in both native entry points. Request-only device enrollment/approval/revocation and short-lived, **review-only** dispatch/claim/resume/cancel are staged behind separate **off-by-default** `CLOUD_REPAIR_DEVICE_ENROLLMENT_ENABLED=1` and `CLOUD_REPAIR_DISPATCH_ENABLED=1` VM flags. The native link displays a non-actionable safety notice. Server-internal, separately encrypted supplemental ingestion and owner-only provenance inspection are now tested with synthetic data, but **no public supplemental upload route or device receipt exists**. **Do not set either flag on live services yet:** native pairing/review UI, server-verified receipts, native upload integration and an actionable dashboard link are **not** implemented or enabled. A claimed request explicitly says `uploadEnabled: false` and cannot start an export. Single-owner, unbacked pilot only. A dashboard request is not evidence that a reading exists on the phone, was authorized by HealthKit/Health Connect, or was successfully uploaded. Do not display a working link or a successful repair until both native apps and server verification are shipped and tested.

## User outcome and defaults

From the authenticated account's retained-export explorer, choose exact owner-calendar dates and reviewed source-specific metric IDs, or **entire selected days**, plus Summary, Detailed Time-Series, or Lossless Health Records where the platform supports that detail. Inspect the estimated scope, source, coverage uncertainty and potential replacement consequences. Create a short-lived queued request and open Health.md with a **static** app link (no health dates, metric names, account identifiers, request IDs, tokens or endpoint values in the URL). On a separately enrolled phone, fetch the scoped work over TLS, show an in-app review, and require the user to confirm before querying the OS or uploading. Use only the already configured, exact Health.md Cloud HTTPS endpoint and that account's write-only token from the native secure store. Never change the saved endpoint, token, metric settings, schedules or export profiles as a side effect. Never fetch retained exports with the write-only token.

Account dashboard evidence states: `not_uploaded` means no current snapshot; `value_unavailable_in_uploaded_summary` means a reviewed projection has no verified value in the current envelope, **not** that the device has a reading or that the metric was excluded by the app; `unsupported_profile` and `read_limit` are not candidate measurements. A captured zero is not missing. A partial/failed manifest requires separate inspection, not a zero. Different iOS/Android statistics must retain distinct identities (e.g. HRV SDNN versus RMSSD). Date selection uses logical owner days in the source calendar time zone; the native review must show/verify the actual day boundary and reject mismatched source/platform/calendar rather than silently change it. When no trusted zone is present, request mobile confirmation; do not infer it from the web browser.

## Snapshot safety — prerequisite for metric-specific repairs

Current `healthmd.api_export` ingestion replaces the *current daily pointer* with the latest accepted envelope for that date; it retains old envelopes as revisions. A metric-only re-export for an already uploaded day would therefore hide every previously uploaded field not repeated in the new snapshot (including providers, time series and archives). **Do not implement metric-specific repair by sending an ordinary partial API export and letting it replace that pointer.**

V1 may allow exact selected metrics on a day with no current snapshot. For an already uploaded day, use a separate, authenticated **supplemental receipt** that stores its original compatibility envelope as an additional encrypted retained export, binds the exact requested metric IDs and owner date to that envelope, and does not replace the primary `daily_records` pointer. **Staged internal storage (migration `0009_supplemental_exports.sql`):** `ingestSupplement` requires an existing write-only ingest token plus a trusted, normalized server-side scope (not a client header), stores the complete encrypted envelope as `exports`, purpose-encrypts the scope under export/account AAD, records matching day pointers only in `supplemental_records`, and never updates `daily_records`. Only the server-internal function can call this path; public ingest rejects `X-HealthMd-Repair-*` headers instead of silently treating them as ordinary replacements. Ordinary API exports retain their established replacement semantics and cannot attest full capture from envelope shape alone. Do **not** direct a phone to the ordinary endpoint for a repair. The owner-only `POST /api/repair/supplements` read model presents primary and supplemental Apple-v8 reviewed summaries **side by side** by exact export ID and record pointer; observed zero and unavailable fields remain distinct. Failure-only envelopes are discoverable but never attributed to a logical owner day from an untrusted failure timestamp. Android and provider data remain original-json-only, not Apple projections. Dashboard and aggregate-only MCP charts stay primary-only; full-export MCP inventory labels `retentionRole: supplemental` for authenticated navigation, without adding tools or merging archives/profiles. An alternative full-day refresh is allowed only as a separate, explicitly confirmed replacement request after the phone shows its actual metric/detail/provider scope and warns that a newer complete snapshot can legitimately change or remove previously reported values. Failure to guarantee the supplemental/non-replacement path is a **blocker to enabling links for existing dates**. The mobile exporter must not mutate a saved profile to carry an ad hoc request.

## Proposed handoff and authority

1. Account session + same-origin browser intent creates a bounded request (maximum 31 distinct logical days per draft; metric IDs must be source-reviewed; a single source/platform per request; detail level explicit). **Implemented draft slice:** `POST /api/repair/preview` compares those dates with current owner-bound retained evidence (Apple metric summaries require verified, bounded decrypt); `POST /api/repair/drafts`, `GET /api/repair/drafts`, and `DELETE /api/repair/drafts/:id` save, list and cancel private, non-launchable drafts. Their date/metric scope is AES-GCM encrypted under a purpose-separated HKDF derivation, with account ID and draft ID as associated data; cancellation erases ciphertext, and maintenance deletes expired drafts. Active drafts expire after 24 hours and are limited to ten; the UI makes no launch or phone-availability claim. Only the eleven reviewed Apple v8 metric IDs and Android **entire days** are currently selectable; unreviewed Android metric aliases and Android lossless mode are refused. The staged review-only dispatch now binds an approved device to an immutable saved draft for at most 15 minutes, with atomic one-device claim, same-device resume, cancellation/revocation and expiry. It is not launchable; a later version still needs authenticated native review, ingest correlation and verified server receipts. Never put the request body in logs, analytics, browser storage or a URL.
2. Phone enrollment is a separate, revocable, **request-only** grant, not an ingest token, MCP reader token, account cookie, or general export reader. App initiates a rate-limited short-code enrollment and keeps a generated credential only in Keychain/Android Keystore-backed storage; account owner confirms the code and device identity in the account session with password step-up. Authenticate every device poll, claim and status receipt. An unenrolled phone or a revoked grant learns nothing about queued scopes. Store only a token hash (or device public key) server-side; never embed it in a link or return retained export payloads to the device grant.
3. **Staged server-only dispatch:** `POST /api/repair/dispatch` binds an authenticated owner's existing draft to one approved same-source device for at most 15 minutes, one active request/device and one dispatch/draft. Owner `GET /api/repair/dispatches` lists metadata only; owner cancellation, draft erasure and grant revocation disable the claim. Approved devices use bearer-authenticated bodyless `POST /api/repair/device/claim` and `/resume` to retrieve only their still-active encrypted-draft scope, and `/decline` to cancel. All return no-store; the account-authority router (public account listener or original private tailnet writer) can serve them, never the separate public write-only ingest origin or MCP. Delivery is review-only and gated off by default until native authorization and upload receipts are complete. A static `healthmd://cloud/requests` (or reviewed platform-equivalent app link) only opens the app. A link by itself conveys **zero** authorization or request selectors and cannot start an export. The app fetches only that device's pending request from the account origin via its scoped grant; the public write-only API and public read-only MCP origins must not serve request reads. Limit claim to one device, protect against duplicate launches/replay/expiry, and expose no health payloads to link resolvers or browser referrers.
4. Native review presents source, exact dates/zone, metric IDs or entire-day selection, detail, estimated volume, existing-day supplemental vs full replacement, destination host, and possible permission/size limits. User must explicitly tap **Export**. If endpoint is not the exact approved `https://api.healthmd.app/api/v1/exports`, or there is no matching stored write-only credential, stop with setup instructions. Do not auto-install a credential, broaden permissions, start a schedule, substitute a tailnet URL or use a different endpoint.
5. Capture and upload through the production API Endpoint runner with immutable per-action scope/destination, existing bounded batches and normal OS permission/lifecycle rules. The public ingest origin may accept a purpose-specific request correlation header *in addition to* the write-only token, but the header is not authority: bind it to the token's account, approved request, selected source and exact day scope at commit time. For supplemental days, ensure transactionally that upload does **not** overwrite the current daily pointer. Do not retrofit historical envelope bytes; this is server-internal metadata/projection versioning. Sidecar-only, no-data, permission denial, failed dates, 413, cancellations and partial batches have distinct receipts.
6. Show a per-day/per-metric outcome only after correlating server-accepted envelopes and their evidence to the request. Phone-reported completion without a verified server receipt is `unverified`, never `uploaded`. A successful upload may still contain no measurement. Inventories, download, explorer and full-export MCP remain owner-scoped and provenance-aware; older and supplemental envelopes remain navigable. Deletion/retention/quota/reconciliation cover the new objects, and all responses are no-store.

## Product scope and version decisions

The staged request grammar, static-link vectors and synthetic review-only dispatch vector with TypeScript API tests live in `packages/contracts/cloud-repair/v1/`; native Swift/Kotlin dispatch conformance and the server-verified ingest receipt protocol/fixtures are still required **before** enabling a working link. The existing Apple daily v8, Android v4/v5, `healthmd.api_export` v1/v2 compatibility bodies and direct protocol v3 stay byte-identical unless a reviewed producer requirement makes a new platform/profile version necessary. This plan does not claim a common public health-data schema change or direct live-iPhone access by the dashboard. Android Raw API Snapshot NDJSON is not accepted by the Cloud receiver. Exact native metric mappings, detail availability and approved selected-date batching must be checked against both platforms; classify any genuine platform-only ability in `packages/contracts/product-capabilities.json`. The CLI and Obsidian plugin remain consumers of original exports, not silent merged repairs.

## Delivery sequence and stop gates

1. **Synthetic server slice complete, not a mobile handoff:** bounded, encrypted account-only drafts; additive supplement metadata and transactional non-replacing inserts; original encrypted envelope, encrypted request scope, 48 MiB/paged owner provenance reads; role-aware full-export inventories; quota, revision/erasure, conflict, replay, concurrency, partial/failure-only, tamper, access-separation and ingress tests. Ordinary compatibility uploads still replace full snapshots as before; a client cannot select the internal supplement path. Define the remaining native allowlists, owner-day/zone fixtures and server-verified request receipts before any phone repair upload.
2. **Server-only, disabled by default:** request-only enrollment, owner password step-up approval, 90-day expiry and revocation; a 15-minute, same-source/same-owner request dispatch, atomic claim, idempotent resume, cancellation and replay/expiry/cross-device tests. No native credential storage/pairing UI, public upload authority or launchable request yet. Test cross-device isolation, stale claims and replay. No live credentials or health data in tests or logs.
3. **Static link detection only:** both iOS and Android reject URL variants and present a non-launching notice. Add native enrollment/review on both platforms using existing exporters and secure stores. Test unsolicited/duplicate links, refusal, lost/locked phone, changed endpoint, missing credentials/permissions, source mismatch, process death and batch interruption. An unapproved link must not call HealthKit/Health Connect or send any request.
4. Add ingest correlation and receipts with transactional provenance. Test both existing-date supplements and absent-day snapshots, one-day partial/empty outcomes and rollback/retry without duplication. Run affected Apple, Android, contract, cloud, CLI/consumer gates. Physical iPhone and Android device QA must verify confirmation and exact destination before announcing a working link.
5. Only then show and deploy the launch link. Preserve tailnet writer :18788, upload-disabled preview :18787, public write-only API, separate account origin and MCP, and unrelated routes. No public signup or durability claim. If any gate is unavailable, leave links disabled and report the blocker rather than ship an apparent one-tap export.
