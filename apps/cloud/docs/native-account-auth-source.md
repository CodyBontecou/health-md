# Native account authorization: disabled source seam

**AS02 synthetic source implementation; no live activation, issuer approval, native qualification, or configuration transfer.** Read the [AS01 design](../../../docs/architecture/account-profile-sync-source-design.md), [account-auth proposal](../../../packages/contracts/account-auth/v1/contract.md), and [approval ledger](../../../docs/architecture/account-sync-evidence-ledger.md). Their owner/privacy/mobile/production gates remain open.

## Runtime boundary

`src/account-auth-v1/` is an isolated, injectable, configuration-only lifecycle module. `SyntheticNativeAuthority` accepts only AS01's five exact reserved-domain synthetic registrations and the synthetic issuer/audience. Its constructor snapshots registration/dependencies; there is no real-environment factory, credential provisioner, browser login implementation, production store, configuration privacy adapter, signup, or deployment configuration.

`createNativeAuthHttp()` without dependencies denies reserved auth routes with `503 unavailable`. The account Worker positively reserves only the exact GET authorization/inventory and POST decision/token/revoke routes. The core router always denies those reservations, including the combined and password VM pilot profiles. Existing `CLOUD_RUNTIME_APPROVED`, cookies, feature-looking request fields, headers, or policy version strings cannot enable issuance. Ingest and maintenance allowlists remain unchanged and deny these paths. The VM account allowlist remains unchanged; there is no VM native-auth listener integration. Existing password/email/export/MCP behavior is preserved.

There is **no global authorization-query exception**. The default account listener continues rejecting query-bearing URLs. Only the separately injected synthetic HTTP adapter accepts the exact authorization URL and closed AS01 query. A future enabled account hook needs separate review of that narrow exception; do not broaden `requestMatchesPublicEndpoint` or the legacy router query rules.

Profile-sync read/mutate are not HTTP routes here. `authorizeConfig` proves native authentication and exact read/write scopes only. It does not enable transfer, assert opt-in, select profiles, approve a privacy policy, parse portable content, or persist configuration. No names/templates/endpoints, health content, native permissions/bindings/jobs/purchases, or execution state enter this module. AS05 owns the separate content contract; AS06 must separately implement reviewed privacy, opt-in and storage gates. Health/request/upload/read/MCP/activation operations deny.

## Source interfaces

- `begin(rawAuthorizationUrl, verifiedBrowserIdentity, trustedRateLabel)` validates the exact registration/query before persisting a bounded browser-bound pending review. It returns only a public authorization reference, client/scope and CSRF requirement. The injected adapter supplies existing browser identity; callers cannot post an account ID or native password/cookie as identity.
- `decide(authorizationId, approve|deny, verifiedBrowserIdentity)` consumes the exact pending review and returns a registered callback only after authoritative proof. Browser identity/session/account are rechecked inside the transaction. Denial creates no code or family. HTTP requires exact Origin and CSRF.
- `token(closedUtf8Json)` atomically consumes code or refresh and returns only verified native configuration tokens. It accepts neither cookies, Authorization/Basic input, client secrets, account IDs, scope changes nor audience overrides. PKCE is real Web Crypto SHA-256, not a fixture predicate.
- `authenticate` resolves the authoritative immutable tuple and current account/family/access lifetime on every call. `authorizeConfig(token, method, exactPath)` recognizes only POST read/mutate with canonical scope requirements. The returned frozen principal is provenance-tracked within that authority instance.
- `assertConfigAtCommit(state, principal, method, exactPath)` must run **inside the future configuration mutation's same authoritative transaction**, in addition to that handler's privacy/opt-in/selection gates. It rechecks the original access proof/expiry, account, family, immutable tuple, generation and operation scopes. A copied/fabricated principal or an earlier generation denies. A separately stored/cached snapshot does not satisfy this contract.
- `nativeSessions` returns only the current family. `browserSessions` returns at most 20 owner-bound redacted families and requires authoritative recent reauthentication. The HTTP browser inventory/revoke paths additionally require same Origin and CSRF. This is intentionally stricter than permitting a merely signed-in inventory request.
- `revoke` implicitly targets the native access/refresh family, or a browser owner's supplied family after recent reauth. Spent refresh digests work only on revoke; they cannot list, read or refresh. Unknown and cross-account browser targets have identical not-found errors. Revocation retries are idempotent and require actual revoked state plus the exact transaction audit marker.

The initial GET does not carry an installation label. First successful PKCE exchange binds the supplied random 32-byte installation label. It is neither app attestation nor a sender constraint; copied bearer tokens remain a risk. `NativeAttempt` is an in-memory callback/generation test seam, not an OS browser, secure-store adapter, refresh coordinator, or complete native account state machine. Native owners must enforce one outstanding attempt per installation, serialize refresh, validate bounded token responses, recheck generation at secure-store commit, and implement signed-out/remote-pending UI and revocation-only retry retention separately.

## Locally reviewed AS02 response metadata: native qualification remains gated

AS01's proposed source policy now pins the thirteen `NativeSessionResponse` members, including **`account_id`, `client_id`, `installation_id`, `session_generation`**. Coordinator local source review aligned the contract with the actual disabled synthetic implementation. This is not named approval, a real registration or qualified native wire/transport/secure-storage lifecycle. Initial source grants retain the exact captured canonical requested scopes; current refresh retains those scopes. Reduced-grant negotiation is not implemented and requires its own reviewed source/fixture change; expansion is forbidden.

**Stable account context:** use `(issuer, environment, account_id)` for an account namespace. `account_id` is the existing server-owned opaque account key established by the trusted browser-identity adapter, checked against the authoritative active-account/browser records, stored in pending consent and the family binding, and returned only after code/rotation postcondition verification. It is not an email, provider subject, installation label, session/family ID, or request-supplied tenant selector. The source accepts canonical lowercase opaque UUIDs (the existing `UserRow.id` shape) and explicit `synthetic-account-*` test sentinels; it does not create/link/migrate accounts. Do not use a family ID or account name to identify offline queues.

Tests verify the same context across different installations/families and refreshes, different contexts for different accounts, immutable family binding through rotation, response provenance against browser/account state, and rejection of posted account overrides/email-shaped response identity. No native caller needs `/api/account`, browser cookies or retained-health scopes to obtain that context. Only a short-lived code, state and issuer use the callback; the account context appears in authenticated TLS token JSON, never in the callback or authorization URL.

`session_generation` is a nonnegative safe server refresh-family generation: **0** for a new family, incremented on refresh, **not** the native account-switch generation. A native attempt separately pins its local generation; sign-out/switch must advance it, stop sync and quarantine old mappings/outbox before any late callback/token/apply response can commit. First sign-in establishes the verified account namespace; refresh must preserve it. This metadata is not account authority when echoed by a caller and must not be accepted as a tenant selector by AS06.

**Precise unmet identity gate:** no live browser identity/account store adapter is installed; no real issuer, callback registration, account linking/recovery/migration or production approval exists. The response/opaque-key grammar received local source review; AS03/04 must still implement and qualify trusted transport, closed response parsing, secure-store and local account-generation fencing. AS06 must derive ownership from freshly verified server principals, never posted context. The synthetic stable-identity proof is not a live credential issuance or physical-client result.

## Atomicity and failure contract

`AuthStore` exposes synchronous callbacks inside a linearizable transaction and fresh consistent reads. All account/browser status, pending/code state, immutable family binding, access/refresh digests, hourly admission counters and fixed-event operation receipts must share the authority. Account disable/deletion and future configuration mutations must serialize with these operations. A backend using cached reads, independent account replicas, non-atomic snapshots, callback retries or per-process locks over independent state violates the interface.

- Pending lifetime: 300 seconds; code: 120; access: at most 300; family: 30-day absolute and seven-day idle maximum. Equality is expired. These are synthetic source security bounds, not approved real retention promises.
- Admission is transactional: 20 starts per purpose-HMAC address/client hour, five decisions per purpose-HMAC account/client hour, 30 token attempts per purpose-HMAC client/installation hour; five unconsumed pending reviews per account/client and 20 unexpired unrevoked families per account. Production abuse/load/global admission and cleanup remain unqualified. An installation label is public and can be changed; its rate budget is not an identity or anti-abuse attestation.
- Codes/access/refresh are independent random 256-bit values with disjoint prefixes and purpose-separated SHA-256 digests. Stores receive no raw token/verifier. Rate keys use injected purpose-separated HMAC; no raw address labels are persisted or logged.
- Code exchange has one winner. Refresh atomically spends one parent and creates exactly one child/access pair with the same binding/scopes. A second use of a retained spent digest revokes the entire family, including the concurrent winner and all its access tokens. No grace window or secret reconstruction exists. Spent proof history must remain available through the reviewed family lifecycle.
- Every mutation generates an unpredictable operation/audit marker. Adapter return values/change counts are ignored. Success requires the **exact** marker and live postconditions on an authoritative read: pending/decision claim, code consumption or parent spend, exact child/access tuple/expiry/generation and active account/family, or actual owner-bound revocation.
- Lost adapter commit reply plus readable exact proof can safely return the held result. Unreadable/missing/partial proof returns `503 verification_pending` and no credential. If the caller loses an already committed response, a code cannot mint a second family and refresh replay kills the committed child; reauthenticate rather than recover secrets from hashes.
- A revoke response without verifiable revocation is pending, never remote sign-out success. Local sign-out must fence immediately even offline; this backend does not implement the native retry vault or erasure UI.

## Actual transaction evidence and durable gate

`test/account-auth-v1.test.ts` uses Node 24's real SQLite: fresh private ephemeral files, WAL/FULL synchronization, two database connections, `BEGIN IMMEDIATE`/commit/rollback, and a single strictly checked synthetic state row. It drives the actual parser, Web Crypto, HTTP and lifecycle operations, not only a happy-path in-memory mock or the AS01 symbolic reducer. Fixtures are synthetic; tests remove only their own ephemeral test files.

Faults cover before-commit exceptions, full rollback, success-returning no-op writes, marker-only writes, mutation without marker, lost commit reply, unreadable verification, account disable before readback and replay after lost issuance/rotation/revocation. Races cover two-connection code/refresh, revoke vs refresh and account disable vs exchange; wrong owners and deleted accounts deny. SQLite connection scheduling is host/JS serialized at transaction boundaries; this is not a multi-region D1 concurrency/load claim.

**Durable/live adapter remains partial:** this test snapshot adapter is not exported, deployable, or suitable for real auth-state storage. No SQL migration was added, avoiding auto-application by the existing VM migration runner while configuration/auth-state privacy/retention/deletion/ops policy is unselected. A production adapter needs purpose-isolated schema/retention, authoritative account/browser bridge, robust primary readback, deletion/expiry/spent-history cleanup and real D1/VM fault/load qualification. An interface plus SQLite tests does not close those gates. Existing health-data deletion does not implement erasure of these proposed auth records.
