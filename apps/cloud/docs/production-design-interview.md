# Public Cloud MVP design interview

**State: intentionally unbacked public MVP; US-only hosting required; native Cloud targets, monthly/annual paid plans, 10 GB lifetime-linked allowance, JSON-only artifacts and warned subscription-lapse retirement selected; $100 planning ceiling withdrawn; no overall design or rollout approval.** These are the owner's answers to the experience interview, not authorization to enable signup, deploy, provision resources, issue agent credentials, move pilot health data or remove the pilot warning. Implementation waits for overall design confirmation and reviewed reconciliation of the earlier production gates. No security/privacy gate is waived by the no-backup answer.

This record changes the product target behind the [experience backlog](production-experience-roadmap.md). The [rollout plan](multi-user-production-rollout-plan.md), [proposed ADR-0008](../../../docs/architecture/adr-0008-multi-user-healthmd-cloud-production.md) and [threat model](production-data-flow-threat-model.md) still describe an invite-first, MCP-deferred, server-decrypting proposal. They need a reviewed revision after the unresolved decisions below; they are not approval of this new target. The [completion audit](production-readiness-audit.md) remains evidence of gaps, not launch readiness.

## Encryption facts checked against source

- [Ingestion](../src/exports.ts) currently receives and parses the original compatibility JSON before [application encryption](../src/crypto.ts). TLS and encrypted storage do not make this provider-blind: plaintext enters the service before encryption.
- The [VM MCP reader](../mcp/reader.ts) receives the server-side export keyring and decrypts account-owned ciphertext. [The server](../mcp/server.ts) returns readable tool results after [token authentication](../mcp/auth.ts). This is not a zero-knowledge architecture.
- The [current full-export scope](mcp-full-export-tools.md) can expose every retained original field, source archive and embedded binary. Aggregate tokens cover a narrower curated Apple-v8 projection. More granular metric/category/date grants are not already implemented by those two scopes.
- [The current threat model](production-data-flow-threat-model.md) includes sensitive dates, identity/authentication state and ownership relationships in server-side metadata. Encrypting content would not automatically hide those facts, traffic timing, account existence or object sizes.
- The official [HTTP MCP authorization specification](https://modelcontextprotocol.io/specification/latest/basic/authorization) describes OAuth-based discovery, client registration, PKCE, resource-bound bearer tokens and scopes when that authorization model is supported. That is access authorization, not a substitute for content encryption or key management. Qualify the exact target clients rather than assuming a pilot bearer header works everywhere.

These are source/protocol facts, not a fresh live-service assessment. Actual client integrations, exact supported versions, authorization/credential lifecycle and provider handling remain unqualified. Q20 permits shared authority but does not establish interoperability or relax account isolation.

## Constraints checked after Q20–Q34

- **Until-revoked grants differ from current pilot credentials.** Dashboard issuance requires a 1–90-day lifetime and the reader checks `expires_at`; there is no qualified public durable-grant/refresh implementation. Do not extend existing pilot tokens, copy their ten-active cap, or treat refresh/reconnect as new grant admission after a future cap reduction.
- **The primary retention decision differs from current split code.** [Runtime validation](../src/index.ts) requires finite revision retention for maintenance and rejects `unlimited`; [the proposed maintenance profile](../wrangler.maintenance.toml) sets 30 days. ## Zero-knowledge alternative: not a v1 requirement

Working distinction for the interview, **not yet an adopted glossary term**: Health.md's storage service would receive encrypted content and lack the secrets needed to decrypt it. The protected parties, exposed metadata, trusted client software and explicitly authorized agent disclosures all need a precise threat model before making that claim.

Advantages:

- A storage compromise or ordinary operator access would not by itself disclose encrypted health content.
- The archive could make a stronger, precisely scoped provider-blind content-storage promise.

Costs and limitations:

- Encrypt before upload on both native platforms; current plaintext compatibility uploads cannot acquire this property through a server configuration change. Any new encrypted Cloud transport requires independent versioning, cross-platform contract review and fixtures; original daily export bytes need not be rewritten to wrap them in a new transport.
- The existing server cannot parse/validate hidden health fields, chart them or answer ordinary plaintext MCP queries without an authorized decryption location. Validation, query indexes, derived projections and dashboard rendering need a new design.
- Restored ciphertext is usable only with user-controlled decryption authority. Account sign-in recovery and archive-key recovery are different problems; a password reset does not automatically recover encrypted data. If the operator can unilaterally recover decryption keys, it cannot claim that it lacks decryption authority. Provider-blind storage may replace the VM-loss warning with a different, explicit lost-user-secret warning; backup ciphertext alone cannot eliminate that risk.
- A browser dashboard adds trust in delivered client code; client/update compromise can steal keys or plaintext. Do not equate an encrypted bucket with protection from every malicious software update.
- An authorized agent receiving readable results, and its model/provider, still sees that disclosed data. Zero-knowledge archive storage does not prevent the agent provider from retaining it. Revocation stops future authorized access; it cannot recall plaintext or keys already delivered.

## Encryption alternatives considered; A selected as the v1 trust model

| Candidate | Where ordinary MCP results become readable | Benefit | Cost / truthful privacy statement |
| --- | --- | --- | --- |
| A: service-side encryption — selected trust model | Health.md's authorized reader decrypts retained exports | Fits the current received-export contract, dashboard and unattended hosted-reader shape | Service/provider can process content. Requires strong isolation, key custody, consent and operations; **not zero-knowledge**. The remaining architecture and rollout are not approved. |
| B: provider-blind archive with a user-controlled reader | User's trusted client/gateway decrypts and serves authorized results | Storage service lacks content keys | The reader must be available for queries and supported by target clients. A local phone/browser reader makes queries unavailable when it is offline; an always-on user-controlled gateway adds operating/setup burden. The agent still sees granted results. |
| C: encrypted private archive plus explicitly shared data | A separately consented service-visible projection or grant enables hosted reads | Can keep unshared content opaque while offering convenient remote queries | Define exactly what becomes service-readable and how it is prepared, updated, scoped and revoked. The shared portion is **not zero-knowledge to the reader/service**. Handing the service a full account key is not fine-grained disclosure. Additional native/projection/key-management design is required. |

A reader that returns plaintext must obtain the plaintext or decryption capability somewhere. Moving that capability to another Health.md-operated process does not by itself make the overall service provider-blind. Specialized confidential-compute or encrypted-computation approaches would need their own verified threat model and feasibility work; they are not an assumed launch solution.

**Consequences of Q5/Q7/Q9:** a user-device-only reader does not meet the availability requirement, and the owner now accepts A's service-decryption trade-off for v1. B would need a separately trusted always-on reader; C would make the whole retained archive service-readable by default while a full grant is active. Neither alternative is a selected launch requirement. No new pre-upload encryption transport is required by Q9; preserve the existing native compatibility bytes and keep any future provider-blind transport separately reviewed.
