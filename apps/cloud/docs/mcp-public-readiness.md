# `mcp.healthmd.app` disposable public pilot — deployment evidence

The public **read-only MCP endpoint is live**, behind a dedicated Cloudflare Tunnel and local nginx proxy. The tailnet-only iPhone export writer, synthetic preview, unrelated port-443 service and `healthmd.app` website were preserved. The owner expressly chose **no backup and no independent external security audit** for this disposable one-user pilot; permanent data or key loss remains possible. This is not a general production cloud launch or a claim of recovery/compliance.

## Verified

- Cloud tests: 36 passing, Node 24 VM build, Worker dry-run without publishing, npm audit with no vulnerabilities, product-capability parity validation and `git diff --check`. Full local Wrangler smoke refused to overwrite the preview's active `.dev.vars` as designed.
- `healthmd-cloud-personal-mvp.service` was stopped for SQLite WAL checkpoint and integrity check, migration `0005_mcp_read_tokens.sql`, staging the group-aware writer and group-read-only data permissions, then restarted. Writer tailnet `/health` and login still return HTTP 200. The upload-disabled preview `/health` remains HTTP 200.
- The MCP process runs as a separate `healthmd-mcp` user with a read-only data mount. SQLite/database-WAL-SHM and encrypted objects are group-readable but not writable; the reader cannot read writer secrets/source or signal its process. Its environment has only the decryption keyring and listener settings. Its bounded read tools and token authentication were exercised locally against stored owner data **without printing health values**.
- A separate `www-data` nginx instance has no access to data or secrets, accepts only `POST /mcp`, suppresses access logs and sets `no-store`. A separate `healthmd-tunnel` user owns only the Tunnel credential. The exact `mcp.healthmd.app` DNS CNAME is proxied through this Tunnel; no existing hostname/route was overwritten.
- Public HTTPS: no Bearer, random write-pattern and random read-pattern credentials returned 401. A **temporary** read token initialized the MCP protocol, listed the six tools and accessed the owner's metric catalog without logging its results; GET and other paths were denied and responses were not cache hits. The temporary token was revoked and its delivery file removed; the same token then returned 401. The owner later authorized an aggregate-only Muse credential; its Secure Vault capture and first client read have not been independently confirmed. A separate full-export Muse credential was later issued after explicit scope consent; no Grokbot credential exists.
- The full-export upgrade passed 36 synthetic tests, Node 24 VM build, Worker dry-run, contract parity, dependency audit and diff check. Both VM services were paused; SQLite WAL checkpoint and full integrity succeeded before migration `0006_mcp_read_scope.sql`. Writer health returned 200 after restart; one pre-existing active token remained `aggregates`. Stopping the reader also stopped its dependent proxy/Tunnel; both were explicitly restarted. Public no-token requests returned 401. The existing Muse token listed exactly six aggregate tools and was denied the new full-export calls.
- A one-day, root-only temporary `full_export` token listed 11 tools and exercised owner-scoped retained-envelope discovery, JSON navigation, exact-byte paging and no-store headers on the public HTTPS route, **without printing health values or identifiers**. It was revoked, its delivery copy removed, and subsequent public authentication returned 401. A separate 30-day Muse full-scope token then verified its 11-tool catalog; its root-only delivery copy awaits the owner's secure capture. The old aggregate-only Muse token remains active until vault rotation succeeds.
- Cloudflare currently returns HTTP 403 to the generic `Python-urllib` user agent, before MCP auth. Curl, Node fetch and a named client user agent reach the endpoint. Muse described a custom VM connector with Secure Vault Bearer-header capture (no built-in MCP settings), but live interoperability is still unverified. Grokbot's exact product/retention remains unqualified.

## Remaining owner/client decisions

The public listener alone does not disclose stored health values: it requires an active read token. Before issuing one to Grokbot or another provider, identify the exact product, confirm remote Streamable HTTP with a securely held Bearer header, inspect its storage/retention policy, and obtain the owner's consent. The owner consented to Muse default Meta conversation handling and later **explicitly authorized full retained-export access** for Muse; the old aggregate-only credential must not be silently upgraded. Migration `0006_mcp_read_scope.sql` was applied in a controlled writer/reader pause; the existing aggregate-only token remained unchanged. A new, distinctly scoped 30-day full-export Muse credential was issued and verified via public `tools/list`; it still needs capture and validation inside Muse's Secure Vault. No token may be embedded in a URL, reused from iPhone exports, or shared via dashboard credentials. Clients needing OAuth require a separately designed connector.

The pilot remains unbacked; no password/key recovery exists. Public-facing product/privacy claims must distinguish this single-user, independently authenticated reader from the opt-in export writer and must not imply durability, third-party certification or general signup. For operations, credential administration and rollback, see [`remote-read-only-mcp.md`](remote-read-only-mcp.md).
