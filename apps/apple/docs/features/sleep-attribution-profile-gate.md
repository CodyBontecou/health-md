# Sleep attribution profile gate

Status: `planned` on Apple and Android. Target: **Issue #104 sleep-attribution-successor-profile-review**.

## Version allocation audit

The 2026-10-08 integration audit found a conflicting draft identity: commit `56611bc65` on `feat/cloud-mcp-pilot` defines daily v10 and `apple_health_data_v10` for Night begins plus WHOOP provider-v2 cycle steps. The external Obsidian plugin's main commit `fd5356c4dd032fed975122f4d691d0fdf6fd804f` already has fixtures for that meaning. The original sleep draft reused those identifiers for Morning ends. The sleep workstream now reserves daily v11 / `apple_health_data_v11` / `apple-v11` instead; historical v8 and the separate WHOOP v10 meaning are unchanged. Saved draft v10 sleep contexts retain their exact marker and remain unavailable, never gaining v11 authority on upgrade. Reader adoption must use this distinct identity before enabling production operations. The independent roll-up schema may use version 11 too; daily and roll-up schemas have separate version domains.

## User and consumer outcome

A daily export must have one stable owner-day meaning for the whole operation. Current Apple daily v8, Android frozen v4 and Android analytical v5 retain `night_begins`: the existing noon-to-noon window and its boundary clipping. No stored preference may change that meaning under the same public identity.

`morning_ends` assigns a whole session to its wake-up date without noon clipping. It changes meaning, even though the existing JSON/CSV/frontmatter shapes can represent the resulting values. It remains unavailable in shipped production capture/export routes. The pickers disable new selection of this mode. Previously stored values remain visible and unchanged, with an unavailable explanation; production captures reject them rather than substituting `night_begins` or exporting zeros.

Successor implementation is owner-authorized, but production qualification is incomplete. Explicit Apple-v11 and Android-v6 native JSON preparation and shared successor rendering are implemented; they do not enable production operations. Historical daily defaults, signatures, API envelopes and direct protocols retain their existing identities. The existing Apple range-summary v9 is independent; the proposed successor roll-up v11 must not repurpose it.

## Operation and persistence authority

Apple's `AppleSleepCaptureContext` freezes timezone and attribution before suspension. `ExportOrchestrator` pins it around the whole operation; `HealthKitManager.fetchHealthData` respects the pin rather than shadowing it with each day's preference. API, connected, direct and report callbacks receive the same captured context. Task-local isolation prevents separate concurrent operations borrowing a pin.

New durable operations carry the context in `ExportSettingsSnapshot`. Pending scheduled/Shortcut requests also have a capture-only context, so legacy Shortcut configuration behavior need not freeze an engine/profile snapshot to retain sleep authority. New Shortcut runs pin before suspension and carry that pin into deferred work. Scheduling uses the saved request context without importing a portable profile's device preference. Only journal-store snapshot encoders opt into persisting `sleepCaptureContext`. Ordinary wire/portable snapshot encoders and canonical request fingerprints omit it, retaining their existing representation. The context's optional `exportProfileID` is an explicit successor discriminator: fresh Morning ends contexts carry `apple-v11`, while historical Night begins contexts omit it. Decoding never invents a missing draft discriminator. A marker alone does not bypass `requireShippedProfile()` or approve production capture. Portable setup does not import capture authority or a device capture preference.

Saved snapshot recovery now validates capture attribution, renderer profile and calendar together before planning additional capture. Pending requests, background exports, scheduled retries, connected corpus recovery and frozen HealthKit settings use this agreement check. Historical Night begins accepts only an Apple-v8 pin with the same captured clock when a pin is present. Explicit Morning ends contract validation requires an immutable Rust/apple-v11 pin, every successor version/registry field, and the same saved clock. Matching successor authority still must pass `requireShippedProfile()`; these checks do not open production capture. Tests round-trip a real packaged-core successor pin, reject downgraded/missing/conflicting authority, and verify that a rejected pending request retains its original stored bytes. Complete durable successor admission and packaged-core downgrade/resume qualification remain enabling work.

Recovery rules:

- A saved `night_begins` context remains authoritative even if today's preference is `morning_ends`.
- A saved `morning_ends` context stays unavailable even if today's preference is `night_begins`.
- A pending operation with no immutable attribution context cannot start additional capture. The application does not invent one from today's settings, rewrite the job, erase its journal or relabel existing items. The user may explicitly request a separate new operation.
- Unreadable or unsupported pending-store payloads reject reads and subsequent mutations with a bounded error; they do not become an empty queue or get replaced by a new save. New Morning ends pending requests use the independently versioned `healthmd.pending_exports.sleep_attribution` v1 envelope at `pendingExportRequests.sleep-attribution.v1`. Historical binaries only know the original `pendingExportRequests` array key; their replacement/removal cannot erase the isolated queue. Updated readers inspect both and reject duplicate identities or unsupported envelope authority without changing either payload. A retry cannot change its saved attribution, renderer pin or clock. Only changed queues are written, and every changed payload is encoded before any write. Removing completed IDs across both keys is independently retryable cleanup, not a cross-key transaction.
- Existing draft jobs retain their original key and authority; reading or retrying them never migrates or approves them. Synthetic tests exercise historical-key replacement, mixed-attribution coexistence, unknown envelope versions, duplicate identities and immutable-clock updates against real UserDefaults storage. This qualifies the pending-request store boundary; background/direct/connected journals, spool ownership and complete downgrade/resume admission remain enabling work.
- Existing captured spool/partition bytes and acknowledged frontiers are not recaptured or transcoded by this repair. Journal versions and existing fingerprint/engine/protocol authorities are unchanged.
- Historical records whose `ExportTimeContext.sleepDayAttribution` is absent retain their historical meaning. An absent field in a *pending operation snapshot* is not evidence that its mutable draft-era preference was pinned.

Android resolves one explicit context across chunks. Its current repository and writer contexts reject `morning_ends` before physical capture/render/upload. Stored preferences are not migrated. The native sleep reducer's proposed-mode tests remain qualification controls; shipped writer controls use the historical rule and include unavailable-context negatives.

## Explicit native JSON preparation

The throwing String/Data/sink/OutputStream entrypoints in `JSONExporter.swift` accept an optional `AppleSleepCaptureContext`. A matching Morning ends context with the `apple-v11` marker selects daily schema 11 and emits complete calendar/UTC/attribution/owner/clipping authority. Missing, draft, conflicting or unowned sleep authority rejects with a static error before authority-related stream bytes are written. Explicit authority is required even on an empty day. Omitted-context historical Night begins callers retain their existing bytes; Morning ends cannot silently become v8.

Machine owner dates use the captured Gregorian calendar, not display date preferences. Nonempty sleep summaries/stages require valid session bounds whose end belongs to that owner date. Whole noon-spanning sessions keep their native quantities, Core classification, stage metadata and recorded instants. Successor timestamps use canonical UTC formatting of the representable Foundation `Date`; this is not a claim of arbitrary source nanosecond precision. The independent `healthmd.healthkit_records` v1 archive retains its original ownership and content.

`WakeDateJSONExporterTests` exercises actual native sleep projection with only the HealthKit IPC boundary replaced by `FakeHealthStore`, then actual JSON streaming. Fold/noon/midnight, empty-day, archive and historical-byte controls pass in both native unit-test hosts. Pending scheduled/Shortcut accepted-job fixtures carry immutable Night begins authority; a separate control proves missing durable authority remains missing and never reaches the runner. These are synthetic preparation/recovery controls, not physical-provider, UI or production-route qualification.

## Concrete Apple planner handoff

`AppleLooseDailyExportPlanner` now accepts an explicitly pinned Rust/apple-v11 operation with a matching captured Morning ends context. It loads registry2 from the packaged core and selects semantic/model/render/plan2 without changing historical build-info defaults. Every version, profile, hash and clock must agree. Missing/draft authority, historical/defaulted pins and mixed-attribution records throw a bounded planning error, never return a legacy exporter. Present successor pins remain immutable; the live rollout policy cannot replace them.

The admitted local/preview boundary is overwrite, metric, `Data Detail: Summary` without archive capture, provider sections, workouts, calendar roll-ups, Daily Note injection or individual tracking. The typed quantity adapter maps captured non-workout summary quantities before historical display rounding, including native unit scaling and distance conversions. Integer counts retain their signed-integer representation; structured text keeps its existing projection. A mixed-metric real-planner regression verifies heart rate, blood oxygen, weight, protein and walking distance precision alongside explicit zero steps, and proves populated unselected fields do not block a steps-only plan. This extends the earlier sleep/activity controls; comprehensive per-field and presentation qualification remains required. JSON uses the explicit native-v11 writer uniformly across empty/populated sleep days. Markdown/CSV/Bases use completed successor projections, not historical native bodies. CSV/frontmatter preserve the admitted source quantities, and metadata-off Markdown visibly declares its captured profile/clock/ownership. Source instants and native Core stay unchanged.

`AppleWakeDateExportPlannerTests` runs real application planning and packaged Rust to inspect public artifact bytes, including an IPC-substituted native sleep capture, all four formats, empty/zero-step days, midnight ownership, metadata-off declarations and incompatible-authority negatives. These are native-host integration controls, not physical-provider or production-capture approval.

Explicit local Apple-v11 requested-range summaries now use semantic profile revision 2 and the independent roll-up v11 identity. Native planner tests retain failed requested bounds, count successful empty captures, preserve whole-session quantities, and emit all four formats through packaged Rust. Metric filtering retains source session bounds only in memory for owner validation while disabled Bedtime/Wake Time fields remain absent; invalid, missing or contradictory bounds reject before JSON stream bytes are written. These controls do not qualify calendar roll-ups or production routes.

Fresh production profile selection/capture, complete quantity/presentation/detail coverage, API/direct/connected routes, durable successor acceptance and signatures/inventory remain incomplete. `requireShippedProfile()` still blocks Morning ends; planner tests do not open the setting. Android's complete presentation/detail coverage, canonical API units and production acceptance also remain gated. Neither platform is ready to enable the setting.

The external reader revision `11f805ae98233517d027317775e2033223c109d7` preserves daily successors and Apple range v11 across JSON/CSV/Markdown/Bases, rejects conflicting same-date or same-window authority, and displays captured range attribution/timezone. Native/core fixture byte hashes pin producer `3cb2a6b1f41675c301e5c3fe7eac35fb74770b4c`. The website and Apple onboarding bundle are regenerated from that reader pin; browser runtime tests parse actual native daily and range JSON. Local reader, website and resource qualification does not prove installation in a real Obsidian vault or qualify production routes.

## Required enabling change

The target above must include all of the following before the mode becomes available:

1. Explicit owner approval of successor public profiles with owner-day, clipping, timezone and exported attribution metadata. Do not invent version approval or reuse Apple v8/Android v4-v5.
2. Reader adoption and mixed-version tests for Apple, Android, shared Rust core, CLI, website, API/direct/connected receivers and the external Obsidian plugin.
3. Approved durable-job profile/context selection, downgrade/resume behavior and migration/rollback rules. Portable configuration remains a separate contract.
4. Synthetic overnight and noon-spanning fixtures through every format and surface, both preference-mutation directions, separate concurrent operations and partial recovery.
5. Native accessibility metadata checks on phone/tablet and VoiceOver traversal with hints enabled. Local model/helper tests are not spoken/device qualification.

Historical signature fixtures must remain byte-identical. Capability/registry projections must be updated by their canonical owner/generator, not by editing generated native output or repinning a historical registry.
