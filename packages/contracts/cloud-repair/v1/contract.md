# Cloud export repair handoff v1 (staged)

**Status:** cross-platform application handoff specification. A non-public, server-internal supplemental retention/read path and a separately gated **review-only**, device-bound request transport exist with synthetic tests. Neither is a device receipt or public upload endpoint. The static link is not an export command and must not be published as usable until the owner-account, iOS, Android, supplemental-ingest authorization/receipts, and physical-device gates all pass. This is separate from `healthmd.api_export` v1/v2, Apple daily v8, Android daily v4/v5, and direct protocol v3; none of their bytes change.

## Outcome and authority

An owner creates a bounded missing-export draft in their authenticated Cloud dashboard. A separately enrolled phone retrieves a short-lived request over HTTPS using a **request-only** credential stored in its native secure store. The phone shows the exact source, owner-calendar dates, metric selection or entire-day scope, detail, verified destination, and replacement/supplement mode. A user confirmation is required before any HealthKit/Health Connect read or upload. The existing **write-only** ingest credential is used solely for sending selected compatibility JSON to the Cloud API origin; it cannot list or claim repair requests. A request-only credential cannot read retained exports, upload health data, use account sessions, or access MCP. No new public signup or cross-account data path exists.

## Link (version 1)

Exact permitted URI bytes: `healthmd://cloud/requests`. There is no query, fragment, userinfo, port, alternate host, trailing slash, encoded character, or embedded identifier. Native handlers match the entire raw URI string before presenting any UI. The link contains no credentials, request selectors, health dates, metric IDs, account IDs, endpoint values, or authorization codes. A launch without a separately approved device grant cannot fetch any request. Opening the link alone **never** queries the OS, changes saved settings, starts an export, or creates a credential. Other registered `healthmd://` paths retain their existing behavior. Browsers must not put sensitive scope in link attributes or page URLs; the link is constant across accounts and requests.

## Draft and request grammar

Internal account draft v1 is `{source: "ios"|"android", dates: ["YYYY-MM-DD", ...], scope: "metric_ids"|"entire_days", metricIds: string[], detail: "summary"|"time_series"|"lossless"}`. Dates are distinct, sorted, Gregorian logical owner days; maximum 31 per request. For `metric_ids`, only reviewed Apple-v8 metric IDs are currently available. Android `entire_days` supports `summary` and `time_series`, not the Android Raw API Snapshot or Apple-only lossless archive. The Cloud preview may label a day not uploaded or a projected field unavailable, but it cannot attest the phone has a measurement, source authorization, or the user's intended timezone. Timezone is reviewed on the phone before capture. Unknown fields, unsupported versions/statistics, failed verification, oversized requests, and mixed sources fail closed.

A staged review-only dispatch requires separate short expiry, a bound owner-approved device, replay protection, authenticated claim and revocation, plus the unchanged purpose-encrypted draft scope. Drafts without those fields remain **non-launchable**; even a claimed dispatch reports `launchable: false` and `uploadEnabled: false` until the upload/receipt contract is implemented. Only its bound device may claim a request. The app must show the approved request's exact source and calendar boundary and compare its configured destination to `https://api.healthmd.app/api/v1/exports` **including scheme, host, port and path**. It must have a stored write-only credential; the link may not install or substitute one. A different saved endpoint, source, metric mapping, permission state or timezone needs an explicit user resolution, never an automatic reroute.

## Review-only dispatch v1 (staged)

The owner session uses same-origin `POST /api/repair/dispatch` with JSON `{draftId, deviceId}`. The server checks both records' owner, platform, expiry, approval and revocation again in the atomic insert; it issues one dispatch ID and `expiresAt` at most 15 minutes away, bounded further by draft/grant expiry. At most one unexpired queued/claimed dispatch exists per device, and a draft is dispatched at most once (a retry after expiry needs a newly reviewed draft). `GET /api/repair/dispatches` returns owner-only **metadata**, never the draft scope. `POST /api/repair/dispatch/cancel` accepts a dispatch ID in the JSON body; canceling the draft erases its encrypted scope and cancels any linked dispatch. No request IDs, scope, credentials or account identifiers go in the static app link.

An approved `hmd_dev_…` bearer may call bodyless `POST /api/repair/device/claim` once, moving a queued request to claimed only if the device, source, owner, grant, draft and dispatch are still active. `POST /api/repair/device/resume` returns the **same active claim** to that device if its response was lost, without issuing a new claim. `POST /api/repair/device/decline` with `{id}` in JSON cancels only that device's claimed request. Concurrent claims, revocation, cancellation and expiry cannot create another claim or confer write/read-export authority. A queued or claimed payload includes only bounded scope, source, expiry, `uploadMode: supplemental_only` and explicit `uploadEnabled: false`; it is **not** evidence of capture, upload or server receipt. The migration reserves a `confirmed` DB state for future receipt work, but this stage never writes it and the owner list reports any such row `unverified`, never successful. The synthetic `fixtures/review-only-dispatch-v1.json` gives the body, bounded claim/empty response and invalid ID vectors; dates in that file are not readings. These account-authority routes are gated off by default with `CLOUD_REPAIR_DISPATCH_ENABLED=1` and device enrollment must also be explicitly enabled. The original private tailnet writer shares the account router; neither the dedicated public write-only ingest origin nor MCP can serve them. No native app currently consumes these requests; leave both flags off on live services.

## Snapshot safety and completion

Every ordinary compatibility envelope is a complete *snapshot for its selected scope*, not a delta. A narrow export for a date with a current daily pointer must not replace that pointer. The server must retain it as a separately attributed supplemental export and show per-field original provenance before any UI treats it as a repaired value. For a new date, an explicit partial scope must be labeled as such; it cannot imply full-day completeness. An existing full-day refresh may replace a day only after explicit in-app review of the actual source/detail/provider scope and a separate replacement confirmation. An ingest correlation header is not authority: the authenticated write token, approved device request, account, date, source, and bound immutable spec must all match at the atomic commit. Duplicate payloads or late/concurrent uploads must not create false completion or change pointers. A phone-reported success without a verified receiver receipt remains unverified; no-data, permission denied, unsupported, partial, cancelled, expired and upload failure are distinct outcomes. The Cloud receiver continues to reject Android Raw API Snapshot NDJSON.

## Cross-platform differences and gates

Both apps accept only the exact static URI; iOS registers its existing `healthmd` scheme and Android adds an exact BROWSABLE intent filter. Each app uses its existing native secure credential storage, permission prompts, calendar semantics, API Endpoint exporter and foreground confirmation UI. Apple v8 metric IDs, HealthKit HRV SDNN and optional canonical archive must never be relabeled as Android Health Connect or provider measurements; a separate reviewed Android mapping is required before Android metric-specific requests can launch. Neither app must modify a saved profile, endpoint, schedule, token, or live export settings as a side effect of following a link. Physical iOS/Android QA, privacy/security synthetic tests and all affected export/contract/consumer gates precede enabling the dashboard link.
